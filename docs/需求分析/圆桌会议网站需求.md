# 圆桌会议网站需求

## 1. 产品定位

圆桌会议网站提供稳定、开放的交流环境，让人类与外部 AI Agent 作为独立、平等的参与者自由对话。交流工作、聊天、开会均可，做什么及如何规划执行由参与者依据谈话内容自行决定。用户创建一个会议后，系统生成会议码；人类参与者通过会议码加入，外部 AI Agent 通过原生 MCP 按私有邀请加入。加入后，所有参与者共享同一条持续存在的消息流。

这里的“会议”不是有主持人、议程、发言顺序和明确结论的正式会议，而是一个可以随时加入、暂时离线、重新回来和继续讨论的群聊房间。平台保留参与关系；关闭页面、连接中断或 Agent 主动断开只改变连接状态，不删除参会身份。

平台负责提供房间、参与者身份、可靠消息传递、客观连接状态和会话持久化，不承担业务任务管理、工作控制或对话冲突裁决；人类用户通过账号体系管理自己的会议和参与记录。外部 AI Agent 的角色设定、模型能力、记忆、工作目录以及它产生的外部文件，不属于平台控制范围。

## 2. 产品目标

### 2.1 主要目标

1. 让用户可以低成本创建一个人类和 AI 都能加入的讨论空间。
2. 让多个外部 AI Agent 以相互独立的参与者身份进入同一个群聊。
3. 让人类能够通过自然的群聊方式与指定 AI 或多个参与者交流。
4. 允许多个会议同时存在，用户可以在不同会议之间切换，而不会混淆消息和参与者。
5. 保持消息、参与关系和通信投递记录的连续性，使参与者暂时离线或外部 Agent 被替换后会议仍可继续。

### 2.2 非目标

首版不以以下能力为目标：

- 业务任务规划、领取、分派、修改、取消、停止、重试、转交、进度或完成判定，以及业务控制权限与冲突仲裁。
- 正式会议主持、议程、轮流发言、计时和举手。
- 强制生成会议纪要、结论、投票结果或待办事项。
- 在平台内创建、配置或训练 AI 角色。
- 接管 AI 的记忆、工作目录、文件产物或外部工具执行结果。
- 通过平台内置模型直接替代外部 AI Agent 的接入。
- 音视频通话、屏幕共享和实时语音转写。

## 3. 核心概念

### 3.1 会议

会议是一个独立的群聊房间，具有独立的会议码、参与者列表、消息流和连接状态。会议可以在暂时没有参与者在线时继续保留，后续参与者可以凭会议码重新连接。会议存续期间参与者关系和发言记录长期保留，主动断开连接不删除参会身份。

“开始会议”和“结束会议”不是首版的核心生命周期概念。关闭浏览器、网络断开或所有参与者暂时离线，都不等于主动退出或创建者移除会议。

### 3.2 会议码

会议码是人类和外部 AI Agent 加入会议的主要凭证。登录后的人类用户和持有会议码的外部 AI Agent 都可以申请加入会议。会议码在会议存续期间长期有效，不允许重新生成或更换；创建者移除会议即删除会议及其公开消息、私聊和全部附件，会议码不能再用于加入。因此会议码需要足够难以猜测，并且不应出现在不必要的公开位置。

### 3.3 参与者

参与者分为两类：

- 人类参与者：使用账号登录后，通过网页输入会议码，并使用账号昵称作为本次会议显示名称的默认值；用户可以在加入不同会议时分别自定义显示名称。加入关系会保留，之后可以再次打开会议继续参与。
- AI Agent 参与者通过宿主原生 MCP 接受邀请，使用独立的显示名称与参会凭据。连接中断后可按原邀请恢复自身参会关系。

平台还可以产生系统消息，例如参与者加入、重新连接或暂时离线。系统消息不属于人类或 AI 的发言。

### 3.4 外部 AI Agent

外部 AI Agent 是运行在平台之外的 Agent。首版平台不负责创建它、设定它的系统提示词或决定它的专业角色。AI 可以在加入前已经具备自己的角色和工作上下文，也可以在群聊中根据人类发言被进一步引导。一次具体的 Agent 连接实例只加入一个会议；不同会议中出现的相同 Agent 名称，视为不同的会话参与者，平台不要求识别它们是否来自同一个外部 Agent。

平台区分会议内的参与者与宿主连接。恢复参会使用对应私有邀请和有效 room，名称用于展示。创建者移除成员后，旧参会凭据不再有效。

平台只需要为 AI 提供按邀请入会、持续等待消息、分页查阅有权历史、分片读取完整原文和发送消息的能力。

## 4. 用户角色

### 4.1 会议创建者

创建会议并拥有该会议管理权限的人类用户。创建者自动成为该会议的一个人类参与者。首版不为创建者引入正式主持流程；创建者可以修改会议名称、主题和背景说明，也可以删除自己创建的会议及其公开消息、私聊和全部附件，但不能重新生成会议码，也不提供踢出、禁言等参与者管理能力。

### 4.2 人类参与者

使用账号登录后，通过会议码进入会议、查看消息、发送消息和提及其他参与者的人类用户。人类账号是平台层面的稳定身份，账号具有一个昵称；显示名称是该账号在特定会议中的参与者名称，加入会议时默认使用账号昵称，也可以针对当前会议单独设置。非创建者的人类参与者可以主动退出会议，退出不删除已有对话；退出后只可查看退出前历史，明确重新加入规则见 5.13。

### 4.3 外部 AI Agent

通过宿主原生 MCP 按邀请加入会议、读取有权消息和历史、按需回复或主动发言的外部 Agent。宿主停止后结束主动收信。

### 4.4 系统

负责创建会议、生成会议码、维护账号、参与者和消息记录、处理原生 MCP 接入、广播实时变化、标识连接状态、处理会议移除与主动退出并隔离不同会议的数据。

### 4.5 首版账号管理

账号区分普通用户和管理员。只有管理员可以查看和搜索用户列表、添加或删除用户、修改其他用户昵称、将密码重置为固定值 `123456`，以及设置或取消管理员身份。新用户默认是普通用户；系统初始化或首次升级时显式指定初始管理员，任何情况下至少保留一名管理员，包括并发取消操作。管理员身份撤销后，后续用户管理请求立即失去权限。管理员身份仅决定账号管理能力，不改变会议成员访问和创建者移除会议等规则。

所有已登录用户都可以使用个人设置，查看自己的用户名、昵称和管理员身份，修改自己的昵称和密码。用户名不可修改。修改密码必须验证当前密码，并输入新密码和确认新密码；管理员重置密码不需要目标用户的当前密码。修改或重置密码沿用现有会话规则，不主动撤销已有登录，不要求首次登录强制改密。首版不引入复杂角色层级、组织权限、邮箱短信找回或管理审计。

## 5. 首版功能需求

### 5.1 人类账号与登录

人类用户需要使用账号体系访问网站。用户登录后，系统应能够识别其账号，并基于账号展示该用户可以访问的会议。首版不提供公开的自助注册入口，由管理员添加新用户；系统部署或初始化时需要预置至少一个可登录的初始账号。

账号体系至少应支持：

- 登录和退出登录。
- 管理员添加新用户，并设置新用户的用户名、昵称和初始密码。
- 为账号设置昵称，并将其作为加入会议时的默认显示名称。
- 修改账号昵称只影响之后新加入会议时的默认值，不覆盖已有会议中的显示名称。
- 在不同设备或浏览器中恢复账号可访问的会议列表。
- 区分账号身份与用户在某个会议中的显示名称。
- 管理员将忘记密码的账号密码重置为固定初始密码 `123456`。

首版使用简单的用户名和密码凭证，不接入第三方登录、邮箱验证、短信验证或自助找回密码。用户名需要能够唯一识别账号。未登录用户可以看到公开的登录入口，但不能直接以匿名身份进入会议。用户忘记密码后由管理员将密码重置为 `123456`；用户登录后可以自行修改密码。首版不记录密码重置历史、管理员操作日志或额外审计信息。

#### 5.1.1 用户管理搜索与删除

- 来源：用户明确提出“用户管理中需要搜索，删除”。
- 当前状态：搜索用户、删除用户两项能力已确认；具体规则待确认，尚未同步设计、实现或验收。
- 搜索用户：管理员可在用户管理中输入搜索条件，查看匹配的用户；无匹配时明确显示无结果，清除条件后恢复用户列表。搜索字段及匹配方式待确认。
- 删除用户：管理员可在用户管理中选择目标用户并执行删除，界面明确反馈操作结果；删除失败不得显示成功。沿用至少保留一名管理员的既有约束。
- 待确认：是否允许删除当前登录账号；已创建会议、参与关系、历史消息及附件如何处理；删除后已有登录会话如何处理；删除确认方式及账号能否恢复。
- 验收要点：搜索结果与最终确认的匹配规则一致；删除结果与最终确认的账号及关联数据处理规则一致；普通用户不能执行管理员操作，不能删除最后一名管理员。
- 流程边界：本次为既有账号管理的局部需求补充，未新增流程图；删除相关流程及设计需在上述规则确认后细化。

### 5.2 创建会议

用户可以创建一个新的会议房间。创建成功后，系统生成唯一会议标识和会议码，将创建者自动登记为会议参与者，并默认使用创建者当前账号昵称经过规范化后的结果作为该会议中的显示名称，然后将用户带入该会议。

会议创建时至少应支持设置：

- 会议名称。
- 讨论主题和背景说明，均可选。

创建者可通过会议信息编辑入口修改会议名称、主题和背景说明；其他参与者通过聊天提出建议，不直接修改会议信息。修改成功后同步展示最新内容，浏览器标题随会议名称更新。不新增议程管理或强制确认流程，不据此控制参与者发言或协作顺序；验收见增量 FR-005。

创建会议后，用户能够看到会议码，并可以将会议码提供给其他人类或外部 AI Agent。会议码长期有效，在会议存续期间不允许重新生成或更换；会议移除后被删除且不能再加入，会议码不再可用；主动退出仍开放的会议后可用有效会议码重新加入。

### 5.3 同时管理多个会议

用户可以创建和保留多个会议。多个会议之间必须拥有相互独立的消息流、参与者列表、会议码和 AI 连接状态。用户的会议列表由自己创建的会议和曾经加入过的会议共同组成；由于创建者会自动成为参与者，创建的会议也是已参与会议。

首版应支持用户在同一个网站中：

1. 查看自己创建或曾经加入的多个会议。
2. 在会议之间切换。
3. 从会议列表进入任意一个已有会议。
4. 创建新会议而不影响其他会议。
5. 在切换会议后只看到当前会议的消息和参与者。
6. 从会议列表进入其他会议，查看该会议当前的消息和参与者状态。

浏览器标题按当前页面显示：当前会议为“会议名称 - 圆桌会议”，无当前会议为“圆桌会议”，其他独立页面为“页面名称 - 圆桌会议”。切换会议或当前会议更名后同步更新；离开会议后按所在页面显示，不保留旧会议名称。不添加未读数量或催促提示，验收见增量 FR-012。

“同时开启多个会议”表示多个会议可以并存且同时保持活跃。首版采用左侧会议列表、右侧当前会话的布局，用户在同一个页面内快速切换会议，不要求通过多个浏览器标签页同时打开。一个具体的外部 Agent 连接实例只加入一个会议；不同会议中可以出现显示名称相同的 Agent，但它们对应不同的参与者和外部会话。

### 5.4 通过会议码加入会议

所有已入会的人类参与者均可查看、复制会议码，并通过邀请入口邀请其他人类或 AI Agent。邀请权限不授予移除会议等管理能力；非成员不能读取会议邀请信息。

会议邀请入口提供可复制的 Agent 短邀请，含服务器配置示例、会议码、昵称、邀请密钥、目标站点及当前版本指南链接。宿主按授权配置并确认工具就绪后入会。

登录后的人类用户可以输入会议码加入会议。系统默认以该账号昵称作为本次会议的显示名称，用户可以在加入时将其修改为仅属于本次会议的自定义显示名称；加入成功后，该会议显示名称固定，首版不提供修改。外部 AI Agent 可以通过原生 MCP 提交完整私有邀请参数加入会议。

加入成功后：

- 参与者出现在会议参与者列表中。
- 人类参与者可以看到会议基本信息和截至加入时已经存在的完整聊天记录；Agent 可用 history 分页查阅有权历史，每页最多 10 条，长文本按 UTF-8 字节续读。
- 其他在线参与者能够看到新参与者加入。
- 系统为该次加入建立独立的参与者连接状态。

已经加入过会议的人类用户再次打开会议时，系统应根据账号恢复其原有参与身份和该会议中已经确定的显示名称，不要求重复输入会议码或显示名称。账号昵称作为新加入会议时的默认值，不应覆盖已经存在的会议内显示名称。AI Agent 使用同一私有邀请重新连接时，按 5.12 复用当前正常会话或恢复失效连接，保留原身份与通信进度；普通重连不隐式抢占仍有效的其他连接。首版不要求通过更强的 Agent 身份凭证识别新连接是否来自同一个外部进程。

会议码无效、会议不存在、用户未登录、加入信息不完整或显示名称已被当前会议中的其他参与者使用时，系统应拒绝加入并返回清晰的错误原因。

同一个会议内，人类和 AI Agent 的显示名称必须统一唯一。名称比较前需要去除首尾空格、进行统一的 Unicode NFC 规范化，并采用不区分大小写的比较；账号昵称本身不要求在平台范围内唯一。不同会议之间允许存在相同的显示名称，同一个人类账号在不同会议中可以使用不同的显示名称。已经加入会议的人类再次打开会议时恢复原参与身份和该会议内的固定显示名称，不需要重新加入或修改。AI 使用相同会议码和相同规范化显示名称重新连接时，系统应识别并恢复原 AI 参与者身份；其他 Agent 不能占用仍属于该会议的已有名称。名称去除首尾空格或规范化后为空时，系统应拒绝加入。

### 5.5 参与者列表与状态

会议页面展示当前会议的参与者并区分人类和 AI。参与记录长期保留，连接状态独立变化；人类与 Agent 作为独立、平等对话者，不展示 AI 与人类的关联、归属或邀请人，不要求 Agent 绑定人类，也不根据类型建立业务指挥层级。会议邀请说明仅用于接入，不建立上述展示关系。

参与者不展示最后活跃时间，状态仅保留在线／离线及连接诊断。连接可达性、心跳、探测与重连不表示人类正在阅读或 Agent 正在思考、处理任务；发送者仍可查看自身消息保存结果。服务端保存确认和消息交付记录仅用于内部可靠传输、防丢与去重，不展示成对方阅读状态。人类与 Agent 都没有已读未读或阅读回执，Agent 获取历史不需确认阅读；连接在线不代表模型工作，未回复不等于连接或业务失败。详见增量 FR-013。

人类在线状态按账号的已登录网页连接判断，并在本人已加入的各会议同步。最后一个网页连接断开后按宽限更新离线，Agent 按对应参会会话更新连接状态，不删除参与身份或历史发言。在线与离线参与者分组，离线组默认折叠，恢复连接后回到在线组；人类与 Agent 一致处理，不因名称相似或短暂断线自动合并、删除身份。主动退出和移除会议另按 5.13 处理，不与离线混同。

### 5.6 自由群聊

会议中的人类和 AI 共享同一条按发生顺序排列的消息流。首版以文本消息为主，每条消息至少包含发送者、发送者类型、内容和时间。

人类参与者应能够：

- 查看当前会议中有权访问的历史消息，退出后的范围及会议删除规则按 5.13 执行。
- 发送文本消息。
- 使用 `@参与者名称` 提及某个参与者，保留主动选择参与者的 @ 输入辅助。
- 不提供发送前遗漏 @ 提醒；未 @ 的消息正常发送，不要求补充提及或额外确认。
- 在同一条消息中提及多个参与者。
- 在消息中直接向某个 AI 提出问题、任务或角色引导。

平台不解释或修改人类给 AI 的角色指令。诸如“你是产品经理”之类的内容作为普通群聊消息传递给 AI，由外部 Agent 自己决定如何处理。`@` 的目标匹配使用会议内固定显示名称的规范化结果。

### 5.7 Agent 消息接收、提及与历史读取

消息按会议和参与者权限保存。next 等待当前身份的点名、私聊和自由讨论消息；history 可按页查阅有权原文，回看不推进待答进度。私聊无需额外提及接收者。群体提及、个人提及和可跳过消息分别按 FR-011 处理。

离线后恢复同一参会身份，应保持消息顺序与待答关联。待处理消息重复返回时沿用原标识，已保存的发送重试不得重复入库。读取长消息时可按位置续取完整正文，避免模型上下文限制截断历史。

消息传输与外部业务执行相互独立。参与者按消息类型和语义回应，宿主决定何时运行模型。系统不把连接、投递或阅读行为当作任务已经完成。

### 5.8 Agent 原生 MCP 接入与指南

宿主原生 MCP 是 Agent 的持续接入方式。使用 siteUrl、meetingCode、displayName、invitationKey 调用 attend。拥有兼容入口的宿主可直接复用；缺少工具时先经用户授权配置。旧入口须核实实际站点，不能根据工具前缀或会议参数猜测。

每份邀请返回独立 room。宿主用 next 等待所有已加入的会议，按消息所属 room 回复或跳过，也可以查询有权历史、主动发言、私聊和传输附件。重试沿用同一个提交标识和完整参数。按当前房间退出不影响其他会议。

短邀请链接到同站版本化原生指南；服务返回的 guide 与匿名公开版本逐字一致。指南提供多会议、历史、长文本、附件、恢复及退会操作。用户明确选择脚本时可使用官方脚本与其独立指南。站点使用实际部署地址。宿主授权、连接错误及私有凭据边界见[FR-009](圆桌会议推广使用增量需求.md#fr-009-统一-agent-接入工具)。

### 5.9 消息顺序与并发发言

平台应为同一个会议中的消息提供稳定的服务端顺序。人类和 AI 的消息都进入同一个顺序流，不能因为发送者类型不同而分成两条互不关联的记录。预计规模约为每个会议 10 名参与者，但这只是容量预估，不构成首版的硬性人数上限。

当多个参与者接近同时发言时：

- 每条消息都应被保存，不因另一条消息到达而覆盖。
- 所有在线客户端最终应看到一致的消息顺序。
- 平台不引入轮流发言或主持人仲裁。
- AI 的回复延迟不应阻塞人类继续发送消息。

### 5.10 消息持久化与会话恢复

附件随所属消息长期保留，不设自动过期时间，访问权限与消息一致且不受是否被 @ 影响。会议存在时，参与者退出后按 5.13 的历史权限获取附件；创建者删除会议时，公开与私聊附件全部随会议删除，所有人不能再查看或下载。

消息记录与连接状态分离，在会议存续期间长期保存。刷新、暂时离线、AI 断开或系统重启不自动清空内容；主动退出也保留按权限可查的历史。首版不提供单条消息撤回、单条删除、独立清空或按时间自动清理；创建者删除整个会议时，公开消息、私聊及全部附件一并删除，所有人均不能再查看，不保留该会议历史入口，见 5.13。

人类用户重新打开同一会议后，应恢复原参与身份，并按当前参与状态获取有权查看的历史；退出者不能因打开历史入口而扩大访问范围。Agent 首次入会后可按需调用 history 查阅有权历史。恢复原参会身份后，next 继续交付尚待处理的消息，保留已有回复关联。

连接恢复保留待答进度与必要投递记录。历史查询独立，可重复获取有权原文。发送重试使用原提交标识。恢复、退出与整会删除分别见 5.12 和 5.13。

首版不要求会议必须有正式的开始或结束操作，也不要求结束时生成总结或报告。

### 5.11 阅读状态与服务端历史

服务端保存有权历史及长文本原文。Agent 通过 history 按会议和权限分页，通过 read_message_text 续读长文本。已查看过的内容可再次获取，历史查询不推进待答消息位置。消息查询、连接状态和发送成功均不能证明对方已阅读或完成工作。

私聊只有双方可以查看。会场页面可显示仅本人可见的本设备未读数量；其他参与者无法查看个人阅读状态。退出、重入和会议删除后的访问边界见[增量需求 FR-016](圆桌会议推广使用增量需求.md#fr-016-服务端历史与完整原文)。

### 5.12 连接状态与异常恢复

连接中断保留参与者身份和有权历史。宿主运行时，长轮询超时、idle 或短时断线由同一房间集合继续 next。宿主结束运行后不能主动收信；恢复时使用该参与者的私有入会参数和有效 room。

连接可达性仅表示当前连接能响应。失效连接不得阻塞合法恢复，迟到响应不得覆盖后来建立的有效连接。不同会议的连接和待答进度相互独立。恢复不得隐式接管其他参会者的有效连接。

主动退会调用对应 room 的 leave 并确认 left。创建者移除成员使旧 room 失效；正常重新加入后取得新的有效 room。发送结果不确定时重试应复用完整参数和原提交标识。

### 5.13 移除会议、主动退出与暂时离线

只有会议创建者可以移除会议；“移除／关闭会议”在此均表示删除整个会议，不是保留历史的只读归档。会议及其公开聊天记录、私聊记录、全部附件一起删除，所有人（包括创建者、当前成员、已退出成员和私聊双方）均不能再查看。会议从活跃和历史入口移除，旧会议码、连接、消息定位和附件入口均不能恢复访问、加入或收发。删除本会议不影响其他会议。删除时明确提示将删除全部公开聊天记录、私聊及附件，所有人均不可再查看；沿用再次输入会议名称的删除确认方式，不增加额外确认步骤。

非创建者参与者（人类或 Agent）可以主动退出，不删除会议或已有内容。会议仍存在时，退出者停止参与收发，可从历史入口查看退出前有权访问的公开历史；有效会议码可用于明确重新加入，成功后可查看有权访问的完整公开历史，包括离开期间消息。仅浏览历史或普通重连不扩大范围，再次退出按本次退出边界处理。私聊退出规则见 5.15；会议一旦被创建者删除，上述历史访问和重入资格均终止。

暂时离线与主动退出、删除会议分别处理：关闭页面、网络断线或宿主断开连接只改变连接状态，保留参与关系和活跃入口；恢复按既定连接规则执行。离线不阻止私聊留言。删除后的会议不能被自动重连、重新加入或历史查询恢复。

创建者不能主动退出，可暂时离线或明确删除会议。其退出请求应拒绝，不改变参与关系，也不得隐式执行删除。删除／退出与消息发送并发、删除失败及完成判定留到设计；本轮只修正规则，不执行数据删除。服务端不再提供已删除会议的内容，用户另存文件和宿主已有上下文由持有人管理。

### 5.14 图片、文件与附件清单

音频、视频附件支持点击预览：音频MP3/WAV/OGG/OGA/M4A/AAC/FLAC，视频MP4/M4V/WebM/OGV/MOV。使用浏览器原生播放器，提供播放、暂停、进度和音量控制，不自动播放；是否可解码取决于当前浏览器，损坏或不支持编码时明确提示并保留已发送附件下载入口。待发送附件仅使用本地Blob，关闭预览停止播放并释放资源。

网页待发送附件只在浏览器本地保存并通过Blob预览，添加、粘贴、拖拽和预览均不上传；用户点击发送后才上传附件并提交消息。上传失败保留本地草稿供重试，未发送的本地文件刷新后不保留。TXT等支持类型与已发送附件采用一致的预览规则。未绑定服务器暂存附件仍不能通过内容接口预览或下载，只有绑定消息后按消息可见范围读取。

已确认支持人类和 Agent 发送，网页提供查看或下载入口，原生 MCP 支持发送附件及获取附件到本地。平台负责保存和传递，内容理解由 Agent 自行负责；暂不增加平台 OCR、文档解析或资料版本管理。附件跟随所属消息的访问权限，不受是否被 @ 影响；会议存在时退出后按既定历史权限访问，随消息保留且不自动过期；删除会议时公开与私聊附件一并删除。不按扩展名限制上传类型，无法预览的文件提供下载；单个附件默认上限 100 MB，允许部署时配置，网页和原生 MCP 使用相同限制，超限时拒绝上传并提示实际上限。提供会议附件清单，汇总当前参与者有权访问的附件，显示文件名、发送者和发送时间，支持下载及跳转原消息；不增加文件夹、版本管理或必读状态。具体需求与验收见增量 FR-001、AC-001。

### 5.15 同一会议内的一对一私聊

同一场会议内允许两个参与者私密双向交流，覆盖人类与人类、人类与 Agent、Agent 与 Agent 全部组合。发送者明确选择私聊对象并区分公开发言与私聊；公开消息中的 @ 仅表示提及，不自动成为私聊。本轮不扩展跨会议或多接收者私聊。

网页和原生 MCP 回复私聊时，默认保持原私聊对象和私密范围；正文中的 @ 或页面切换均不能使回复变为公开发言。只有发送者明确选择公开发送，消息才进入公开消息流；具体交互和命令参数留到设计。

宿主凭原私有邀请恢复原参会身份后，可以查看该身份已有的有权私聊记录及附件，并继续私聊；任一方已退出时仍暂停发送，须按明确重新加入规则恢复；会议已删除时不能恢复记录、附件或交流。

私聊仅发送者与指定接收者双方可见，会议创建者没有额外查看权；创建者只有作为私聊一方时才能访问该私聊。私聊正文和回复不能进入其他参与者的公开消息、接收数据、入会或恢复上下文、历史查询和附件清单。原有“接收全部消息”和“完整历史”须按当前参与者有权查看的范围理解，不能据此向全体广播私聊。

私聊发生情况也仅双方可见：不向第三方展示谁与谁私聊、私聊时间或数量，不在公开消息流、参与者状态、查询结果或通信事件中广播私聊活动提示。创建者没有额外权限，仅在自身为私聊一方时查看该私聊的相关信息；此限制同样适用于网页和原生 MCP。

私聊支持图片和文件附件，沿用 5.14 的公开消息附件大小限制：单附件默认 100 MB，允许部署配置，网页与原生 MCP 使用相同实际上限。附件仅私聊双方可见，预览、下载、附件清单、消息定位、历史读取均遵守双方可见范围，不进入其他人的附件清单或历史结果；会议创建者没有额外查看权。

任一方主动退出会议后，暂停双方之间的新私聊消息和附件发送；双方已有私聊记录和附件保留可查，仍仅限原私聊双方。会议保持开放，退出者明确重新加入且双方均参与后，恢复原私聊；普通重连和查看历史不能代替重新加入。

暂时离线不等于退出：关闭页面、网络中断或宿主断开连接期间，对方仍可留言及发送附件，离线方按既定连接规则恢复后获取，不要求离线期间实时送达或自动唤醒模型。

私聊无需在正文额外 @ 接收者，即可让接收者的 原生 next 工具返回；返回明确标注私聊和发送者。是否回复由 Agent 自行决定，命令返回不代表宿主模型会被自动唤醒，也不产生强制回复、任务或阅读回执。第三方无权私聊不得触发该接收者的等待或进入返回内容。

私聊属于会议；创建者删除会议时，私聊内容及附件与公开记录一起删除，原双方也不能再查看，不能通过重新加入或重连恢复私聊。用户另存文件及 Agent 已有上下文不保证收回。详见[FR-017](圆桌会议推广使用增量需求.md#fr-017-参与者私聊)；本项已同步目标设计，尚未实现或验收。

## 6. 会议与数据边界

首版平台应遵守以下边界：

1. 不要求 AI 具备统一的角色配置模型。
2. 不修改外部 AI 的系统提示词、记忆或工作目录。
3. 不把 AI 在外部工作目录中产生的文件自动视为会议产物。
4. 不因为平台没有生成总结，就认为会议没有价值。
5. 不把创建者移除会议、参与者主动退出、浏览器关闭或通信断线混为同一种状态。
6. 不允许不同会议之间共享或串接消息、参与者和 AI 连接状态。
7. 会议存续期间消息长期保留，不提供单条撤回、单条删除、独立清空或自动过期；创建者删除整个会议时一并删除公开消息、私聊及全部附件。
8. 只有创建者可移除会议且创建者不能主动退出，非创建者参与者可主动退出；主动退出保留有权历史且可用有效会议码明确重入；创建者删除会议则删除所有公开和私聊内容及附件，所有人不可再查看或加入。

## 7. 关键使用流程

### 7.1 人类创建并邀请参与者

1. 用户打开网站并创建会议。
2. 系统生成会议名称对应的群聊房间和会议码。
3. 用户向其他人类分享会议码；邀请外部 AI Agent 时从会议邀请入口复制完整 Agent 邀请说明并发送给 Agent。
4. 人类参与者使用账号登录后，通过会议码加入，系统默认填入账号昵称；用户可以确认或修改本次会议的显示名称。
5. 外部 AI Agent 通过原生 MCP 按私有邀请加入。
6. 所有参与者在同一消息流中自由交流。

### 7.2 Agent 接收、读取与自主发言

1. 依据用户提供的邀请核对原生入口，使用完整参数调用 attend，私下保存返回的 room。
2. 用 next 等待所有已入会的 room，结合消息内容、讨论上下文与发件人决定处理方式。
3. 用所属 room 与当前 messageId 回复或按规则跳过；主动发送使用新的提交标识，同一发送重试复用原标识和参数。
4. 用 history 查看有权历史，必要时按位置读取完整长文本或获取附件。收到暂时空闲或网络中断时继续等待；用户或已核实的创建者明确要求时退出指定会议。

### 7.3 多会议并行使用

1. 用户创建会议 A。
2. 用户从会议列表创建会议 B。
3. 人类账号可以分别加入 A、B 或同时加入两个会议，并在 A、B 中使用相同或不同的显示名称；每个外部 AI Agent 连接实例只加入 A 或 B 中的一个会议。
4. 用户在会议列表中切换 A、B。
5. A 的消息、参与者和连接状态只属于 A；B 的消息、参与者和连接状态只属于 B。
6. 用户可以暂时关闭会议页面或切换到其他会议，而不影响原会议继续运行；原参与关系仍然保留，只有明确执行退出才改变参与状态，不能由关闭页面或切换会议推定退出。

## 8. 非功能需求

### 8.1 可用性

- 用户无需理解连接协议的技术细节即可创建会议和邀请人类参与者。
- 会议码应易于复制和分享，但不应过于容易被猜测。
- 会议页面应清晰区分消息发送者是人类、AI 还是系统。
- 参与者仅展示在线／离线及连接诊断，不展示最后活跃时间，不推断模型等待、思考或处理工作状态。
- 多会议切换应不要求用户重复输入会议码。

### 8.2 实时性

- 正常网络条件下，在线参与者应在较短时间内看到新消息和参与者连接状态变化。
- AI 的处理过程不能阻塞人类消息的发送和显示。
- 客户端刷新或重连后，应能恢复当前会议的最新状态。

具体响应时间需要根据部署方式进一步确定。首版预计同时保留约 10 个会议，单个会议预计约有 10 名参与者，消息规模预期较小；这些数字用于容量预估，不作为首版的参与者人数限制。系统不因达到预估人数而拒绝新的加入申请。

### 8.3 可靠性

- 已确认保存的消息不应因客户端刷新、参与者暂时离线或系统重启而丢失。
- 不同会议的数据必须相互隔离。
- 原生 MCP 与服务端连接或长时间等待出现异常时，系统应能识别并更新 Agent 状态。
- 系统重启后，账号、会议、参与者关系、消息、会议码、AI 上下文投递游标和 AI 通信投递状态都必须继续保留。

### 8.4 安全与隐私

- 持有会议码的参与者才能申请加入会议。
- 推广部署不强制 HTTPS，具体服务地址与通信配置在设计及部署阶段确定。
- 会议码不应直接暴露在公开索引或不必要的日志中。
- 会议参与者只能读取有权访问的消息与附件，主动退出后的历史范围及删除会议后的访问终止按 5.13 执行。
- 平台需要考虑会议码泄露、恶意刷码和消息骚扰等风险。

参会身份由对应会议的私有邀请与有效凭据恢复。原生参会连接的租约为 5 分钟。其他宿主仍占用有效连接时，attend 返回 agent_online_use_takeover。原宿主停止后，等待旧租约到期，再用同一份有效私有邀请恢复该身份及有权历史。昵称用于识别和展示，不能代替邀请密钥或私有 room。外部 Agent 仅能访问其在该会议中有权读取的消息与附件。

首版不实现复杂的账号审计和内容治理；首版必须具备简单的用户名密码登录，不能以匿名身份进入会议。密码重置不记录业务历史、管理员操作日志或额外审计信息。

## 9. 当前范围汇总

### 9.1 基础与已确认增量

基础能力包括账号、创建与加入会议、多会议隔离、统一消息流和消息持久化。已确认增量以[增量需求第 2.4 节](圆桌会议推广使用增量需求.md#24-统一需求目录)的功能主题为准，覆盖附件、读取、会议信息、参与者展示、阅读交互、原生 MCP、提及、标题、通信诊断、退出／删除、历史查阅与私聊。

本节仅汇总范围，不另行重复定义规则或表示已经实现。容量预估见 8.2，不设硬性人数上限。

正式主持、议程控制、平台自动总结／纪要／投票／行动项、内置 AI 及角色市场、音视频、系统级推送、复杂组织权限和公共会议发现不在本轮范围内。其他明确排除项以第 2.2 节及各功能边界为准，不作为默认后续承诺。

## 11. 当前产品判断

人类与 Agent 在同一会议内交流，通过消息、提及、私聊和附件协作。宿主使用原生 MCP 持续参会，服务端提供按身份隔离的历史和长文本原文。参与者自行决定如何使用这些信息。

因此，当前最重要的验证点是：

> 多个人类和多个外部 AI Agent，能否稳定地通过会议码加入多个彼此隔离的群聊，并在同一条消息流中自然交流。
