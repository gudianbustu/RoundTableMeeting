# 账号访问与用户管理主题总体设计

## 1. 文档定位

本文是“账号访问与用户管理”主题的总体设计，只负责确定本主题的目标、范围、跨端身份契约、子文档分工、主题依赖和完成门槛。服务端、客户端、模块、页面和组件的具体设计分别由本目录下的子文档负责。本目录编号为 003，对应[总体设计](../001-总体计划/design.md)中的“主题二：账号访问与用户管理”；后续文档中的“主题三”指总体设计中的下一业务主题“会议工作台”，不是目录编号 003。

本主题的产品依据为[圆桌会议网站需求](../../需求分析/圆桌会议网站需求.md)和[圆桌会议网站总体设计](../001-总体计划/design.md)。需求分析文档保持产品需求完整；001 总体计划记录了首轮最小登录范围，本次由用户明确重新开启最小用户管理增量，继续维护在 003 主题内，不创建新的业务主题目录。

用户管理增量已经按本目录的设计、实现方案和测试方案落地；后续修改继续以当前文档为有效契约。此前的审查与修复报告只评价首轮登录切片，不作为阻止本次用户明确重新开启范围的约束。

系统框架前置项已经由提交 `4abd58e` 完成：Origin 写请求保护由 endpoint routing 和 method-level metadata 驱动，不再硬编码 POST，已覆盖标记端点的 POST、PATCH、PUT、DELETE。003 用户管理可以直接使用 PATCH 表达昵称修改，不再等待框架升级。

## 2. 主题目标

本主题的目标是以最小成本提供稳定的人类登录身份，并允许内部测试人员补充测试账号，使后续会议、群聊和 AI 协作主题能够快速组织多账号验证。

主题完成后必须能够：

1. 从配置初始化可登录的预置账号；任何部署至少一个有效账号，验收环境至少提供两个账号。
2. 使用用户名和密码登录。
3. 保持登录状态，页面刷新时不要求重新输入凭证。
4. 获取当前账号的稳定 `UserId`、用户名和昵称。
5. 主动退出登录。
6. 统一拒绝未认证的受保护页面和业务接口。
7. 让后续主题复用统一当前用户上下文，不自行解析 Cookie 或客户端身份状态。
8. 查看平台中的最小用户列表。
9. 添加可登录账号，并设置用户名、昵称和初始密码。
10. 修改账号昵称。
11. 将账号密码重置为固定值 `123456`。

## 3. 本次实施范围

### 3.1 必须实现

- 配置驱动的账号种子和幂等初始化。
- 用户名密码登录。
- 服务端 Cookie 会话。
- 当前用户查询。
- 当前浏览器退出登录。
- 最小登录页、认证状态初始化、登录后占位页和当前用户显示。
- 统一的认证中间件、授权边界和 `UserId` 当前用户上下文。
- 密码不可逆哈希、错误响应脱敏和认证日志敏感信息保护。
- 所有已登录用户可访问的用户列表。
- 所有已登录用户可添加账号、修改昵称和重置密码。
- 密码重置固定为 `123456`，不提供自定义重置值。
- 用户管理菜单和 API 暂不做角色或权限区分。

### 3.2 明确不在本主题实现

下列需求在产品需求文档中继续保留，但本次不实施：

- 用户搜索、分页、公开注册和批量导入。
- 修改用户名、头像、偏好或昵称以外的个人资料。
- 用户自行修改密码、忘记密码、自助找回密码和首次登录改密。
- 账号启用、禁用、删除、合并、迁移和完整生命周期管理。
- 普通用户、管理员、组织、团队和细粒度权限。
- 多因素认证、第三方登录、邮箱或短信验证。
- 登录历史、密码重置历史、管理员操作审计、异常登录识别和高级限流。
- 多设备会话管理、强制退出其他设备、设备管理和长期免登录。
- 头像、通知、个人设置和用户偏好。

这些延期能力只有在会议、群聊和 AI 协作核心价值验证完成，并由用户重新确认优先级后，才建立新的需求和设计。当前四项用户管理只适用于少量可信内部测试人员，所有已登录用户拥有相同能力；进入生产或对外环境前，必须通过菜单认证、API 认证、审计和会话治理收紧，不得直接沿用本轮开放边界。

## 4. 跨端身份契约

### 4.1 人类账号

人类账号是平台范围内稳定的人类身份，至少包含：

- `UserId`：系统生成、长期稳定的账号主键。
- `Username`：登录使用的账号名称；本主题不提供修改。
- `Nickname`：账号昵称；会议内显示名称规则由后续会议主题定义。
- `PasswordHash`：服务端密码哈希器生成的不可逆凭证摘要。

后续业务只能使用 `UserId` 关联会议创建者、会议参与者和消息发送者，不能使用用户名或昵称代替身份主键。

### 4.2 用户管理契约

用户列表和管理操作只暴露 `UserId`、用户名和昵称，不返回密码哈希、配置来源或会话信息。用户名创建后不可修改；昵称修改只更新账号资料，会议内显示名称规则由后续会议主题定义。

添加账号时由操作人输入用户名、昵称和初始密码，服务端复用账号种子与登录相同的规范化和哈希约束。密码重置不接收新密码参数，固定写入 `123456` 的新哈希。密码重置不撤销既有 Cookie，会话撤销留待后续安全主题。

当前不定义管理员或权限 Claim。用户管理页面、菜单和 API 对所有已登录用户开放；未登录请求仍由现有认证边界拒绝。

### 4.3 当前用户上下文

服务端向 Application、Controller、浏览器实时入口和其他人类业务入口提供统一请求级当前用户上下文：

- `IsAuthenticated`；
- `UserId`。

用户名和昵称属于账号资料，不放入请求级身份上下文，也不依赖 Cookie Claim 作为事实来源。需要显示或使用账号资料时，由账号查询用例根据 `UserId` 读取并返回 `UserId`、用户名和昵称。未认证请求的上下文表示匿名，由统一授权边界返回 `401`。业务入口不读取认证 Cookie 内部格式。

### 4.4 会话语义

采用服务端 Cookie 会话。登录成功后，页面刷新和站内路由跳转保持登录；客户端内存状态丢失时，通过当前用户接口重新读取身份，这不是重新登录。认证票据固定有效 8 小时且不滑动续期；Cookie 不写持久化 Expires，浏览器关闭后的实际保留行为不作为本主题承诺，票据到期后必须重新登录。服务端重启后的会话恢复、跨设备会话管理和会话撤销均不属于本主题承诺。

## 6. 后续主题依赖

主题三依赖本主题输出的：

1. `UserId` 稳定身份。
2. 当前用户上下文。
3. 统一 Cookie 认证和授权边界。
4. 当前用户昵称读取能力。

主题三创建会议时以当前 `UserId` 作为创建者；恢复或创建人类会议参与者时同样使用 `UserId`。主题四及后续主题继续复用同一认证边界，不重新实现登录和 Cookie 解析。

## 7. 完成门槛

本主题只有在以下结果全部成立时才算完成：

- 验收环境至少有两个配置预置账号，初始化过程幂等。
- 两个账号都能从浏览器登录，并在主题验收占位页显示各自的 `UserId`、用户名和昵称；主题三替换占位页后不要求继续展示 Guid。
- 登录后刷新页面仍保持登录，不要求重新输入用户名和密码。
- 退出后当前浏览器无法继续访问受保护页面和接口。
- 未认证请求统一得到 `401`，登录失败不泄露账号存在性。
- 密码只以不可逆哈希保存，响应和日志不泄露密码或认证 Cookie。
- 主题三能够直接依赖当前用户上下文获得稳定 `UserId`。
- 主题实现没有引入本设计列明的延期账号生命周期、安全治理或高级会话能力。
- 任意已登录测试账号可以打开用户管理页，查看全部账号并添加新账号。
- 新账号可以使用创建时设置的密码登录。
- 昵称修改后用户列表与当前用户显示按需要刷新；会议内显示名称规则由后续会议主题定义。
- 密码重置后登录密码固定为 `123456`，此前不同于该固定值的旧密码不能再用于新登录；现有 Cookie 不承诺立即失效。
- 用户管理没有引入角色、权限、审计、禁用、删除、搜索或分页。
- 系统框架的 Origin 写请求保护已经支持 POST、PATCH、PUT、DELETE，且用户管理昵称修改以 PATCH 通过同一安全边界。

实现步骤和测试矩阵分别放入本主题后续的 `impl.md` 和 `testPlan.md`；子文档不能借实现细节扩展本主题业务范围。
