# 实时群聊主题总体设计

## 1. 文档定位

本文是“实时群聊”主题的总体设计，负责确定统一消息核心、实时传输、参与者在线状态、提及记录、跨端契约、子文档分工、前置依赖和完成门槛。本主题目录编号为 005，对应[总体设计](../001-总体计划/design.md)中的“主题四：实时群聊”。本文使用目录编号指代已完成主题：目录 002 为系统框架、目录 003 为账号访问与用户管理、目录 004 为会议工作台；“总体计划主题五”指后续 AI 参会主题，对应目录 006。

本主题的产品依据为[圆桌会议网站需求](../../需求分析/圆桌会议网站需求.md)、[圆桌会议网站总体设计](../001-总体计划/design.md)和已完成的[会议工作台主题](../004-会议工作台/design.md)。会议工作台已经提供会议、会议参与者、成员授权、参与者名称唯一性和删除访问屏障；本主题在这些边界之上建立消息与实时协作能力。

“实时群聊”是消息能力主题，不是“人类聊天”主题。会议中的人类参与者、AI Agent 参与者和系统都必须通过同一条服务端排序的消息流出现。当前阶段只实现浏览器人类参与者的发送和接收适配；后续 AI 主题接入 MCP、上下文投递和回复任务时，必须复用本主题的消息实体、追加服务、提及记录、历史读取和实时广播，不得再建立 AI 专用消息表或平行通道。

## 2. 主题目标

主题完成后，会议参与者应能够在同一工作台中：

1. 读取当前会议的完整文本消息历史。
2. 通过浏览器发送文本消息，消息进入与未来 AI 消息相同的持久化顺序流。
3. 在消息中使用 `@参与者名称`，由服务端按会议工作台既有的 NFC + `ToUpperInvariant()` 规则解析为稳定的目标参与者引用并保存提及出现记录。
4. 在多个浏览器之间实时看到消息追加、参与者在线和离线变化。
5. 在发送失败、刷新页面、短暂断网或实时连接重建后获得明确状态，并从服务端恢复已经保存的消息。
6. 在多个会议之间切换时只看到当前会议的消息、提及和在线状态。
7. 在会议删除进入 `Deleting` 后立即停止读取、发送、订阅和状态广播；删除恢复器能够清理本主题新增的数据。

本主题的交付重点不是某一种客户端或 Agent，而是一个可以被多种入口复用的消息核心：消息写入方式可以不同，发送后处理方式可以不同，但消息身份、顺序、持久化、授权、提及和广播规则只有一套。

## 3. 核心设计判断

### 3.1 参与者优先，而非发送者通道优先

`MeetingParticipant` 是消息作者和提及目标的统一身份。`ParticipantType` 只描述参与者属于 `Human` 还是 `Agent`，不决定消息存储位置，也不决定消息能否进入群聊。系统消息没有会议参与者身份，但仍作为同一消息流中的 `System` 作者出现。

消息入口可来自浏览器 HTTP、未来 MCP 或内部系统服务；入口只负责把外部请求转换为统一的消息提交命令。消息提交命令必须交给同一个追加服务，不能由 Controller、SignalR Hub、MCP Handler 或 AI 任务直接操作数据库。

### 3.2 接收与处理分离

所有参与者都可以接收符合其授权范围的消息。浏览器把消息渲染到时间线；未来 AI 连接根据自己的上下文游标选择消息并进入 AI 任务处理；系统处理器可以根据消息追加事件维护提及任务或其他状态。接收方式和后处理器不能改变消息已经进入统一顺序流这一事实。

本主题只保存通用提及记录和持久化消息追加事件，不创建 AI 回复任务，也不自动把某个会议业务动作转换为系统消息。后续 AI 参会主题负责消费面向 Agent 的提及，AI 连续性主题负责投递游标、任务状态和接管；这些扩展不得改变本主题消息 DTO 的既有字段语义。系统消息只保留受信内部追加契约，具体业务触发和与既有事务的整合由产生该事实的后续主题单独冻结。

### 3.3 持久化事实优先于实时通知

数据库中的消息、提及记录和待分发的消息追加事件是事实来源；SignalR 连接、进程内订阅和浏览器内存只承担通知和临时状态传递。服务端必须先在事务中提交消息和追加事件，再广播。广播失败不能撤销已保存消息；客户端连接恢复后通过消息历史接口补齐。

## 4. 本主题范围

### 4.1 必须实现

- 面向 `Human | Agent | System` 作者类型的统一文本消息模型。
- 每个会议独立的严格递增服务端顺序、稳定消息标识和服务端 UTC 时间；正常追加事务不产生序号空洞，但客户端仍需防御实时投递缺口。
- 人类浏览器发送入口、历史读取入口和实时订阅入口。
- 消息内容规范化、空消息和超长消息校验，以及安全错误边界。
- 保存消息中每一次合法 `@` 的文本出现范围；后续处理器按 TargetParticipantId 去重业务目标，保证同一消息对同一 AI 只创建一个任务。
- 以会议参与者稳定标识保存提及目标，不把显示名称作为后续处理的唯一事实。
- 消息追加幂等提交，网络重试不会产生重复的人类消息。
- 持久化的 `MessageAppended` 事件，供实时广播和后续 AI 任务处理器独立消费。
- 浏览器实时广播、按消息顺序补齐、重复去重和连接状态反馈。
- 面向所有参与者的 `online | offline` presence 契约，并在本阶段接入人类浏览器连接；状态与参与者长期关系分离。
- 会议删除访问屏障、消息和提及清理登记、实时订阅终止和删除后的不可读、不可写验证。
- OpenAPI/Kiota 的历史与发送契约，以及可重复的真实浏览器验收路径。

### 4.2 明确不在本主题实现

- MCP Agent 入会、连接租约、接管和上下文字符数协商。
- AI 回复任务、上下文裁剪、任务重试、回复幂等和服务端重启后的 AI 任务恢复。
- AI 主动发言、AI 专用消息通道或 AI 专用历史表。
- 多 Agent 协作链、循环保护和 AI 速率策略。
- 未读数、已读位置、跨设备通知、消息删除、消息编辑和消息搜索。
- 会议总结、投票、主持、议程和正式结束状态。

这些能力可以在后续主题中增加处理器、入口和从属数据，但必须继续调用本主题的消息追加边界，并把新增资源登记到会议删除闭环。

## 5. 统一领域模型

### 5.1 MeetingMessage

`MeetingMessage` 是会议内所有文本消息的持久化实体，至少包含：

- `MessageId`：服务端生成的稳定 `Guid`，对外投递和客户端去重使用。
- `MeetingId`：所属会议；消息不能跨会议读取或广播。
- `Sequence`：会议范围内从 1 开始递增的 `long`，由服务端在追加事务中分配；`(MeetingId, Sequence)` 唯一。为保证 JSON/TypeScript 精确表示，上限固定为 `9,007,199,254,740,991`（`Number.MAX_SAFE_INTEGER`），达到上限后拒绝继续追加并记录运维错误。
- `AuthorParticipantId`：参与者消息必填，系统消息为空；引用目录 004 创建的稳定参与者标识。
- `AuthorKind`：传输值固定为 `human | agent | system`。人类和 AI 作者必须与参与者类型一致，系统作者不能伪装成参与者。
- `AuthorDisplayName`：追加时从参与者快照下来的显示名称；用于历史稳定渲染，不能由客户端提交。
- `Content`：经过服务端 NFC 规范化和首尾空白处理的文本正文；保留内部空白和换行。
- `CreatedAtUtc`：服务端 `TimeProvider` 生成的 UTC `DateTimeOffset`。
- `ClientSubmissionId`：统一提交幂等标识；人类浏览器和未来 Agent 使用外部客户端/任务 Guid，系统消息使用由 `SystemMessageCode + 稳定业务发生键` 派生的确定性 Guid。持久化值对所有消息均非空，同一会议、同一作者和同一标识只能对应一条成功消息。

消息实体不保存“是否已被 AI 处理”“是否在线”“是否已读”等派生状态。AI 处理进度属于后续 AI 主题，浏览器已读状态不属于首版。

### 5.2 MessageMention

`MessageMention` 表示一条参与者消息中解析出的目标引用，至少包含：

- `MentionId`：稳定 `Guid`。
- `MessageId`、`MeetingId`：所属消息和会议。
- `TargetParticipantId`：解析后的稳定参与者标识。
- `TargetDisplayName`：解析时的显示名称快照，便于历史展示和诊断。
- `StartOffset`、`Length`：消息正文中的 UTF-16 代码单元范围，供 .NET 与浏览器使用同一索引高亮；范围以服务端规范化后的正文为准。

同一消息可以对同一目标保存多条不重叠的提及出现记录，每条记录对应一个可高亮文本范围；一条消息也可以保存多个目标。提及出现记录不是 AI 任务，后续 AI 主题在消费时先按 TargetParticipantId 去重，再根据作者类型、目标 `ParticipantType` 和自身任务状态决定是否创建一次任务。

### 5.3 MessageAppendedEvent

消息和提及记录持久化时，同一事务写入稳定 `EventId` 的 `MessageAppendedEvent`。事件只引用已提交的消息和必要元数据，不复制会议码或认证信息。实时广播器、未来 AI 提及任务创建器和其他处理器拥有独立消费进度；某个处理器成功不能替代另一个处理器的确认。

当前主题至少实现实时广播消费。后续 AI 主题新增持久化消费者时，只处理含目标 Agent 提及且在该能力启用后产生的事件，不把旧的人类提及追溯创建为 AI 任务。

### 5.4 MessageAuthorKind 与 ParticipantType

`ParticipantType` 继续沿用目录 004 的参与者身份契约，只允许 `human | agent` 两种参与者类型。消息层增加 `AuthorKind` 的 `system` 值，以表达加入、重新连接或其他平台事实。

`AuthorKind` 是消息作者快照，不是处理器路由。处理器可以根据作者类型选择不同策略，但不得因此把消息写入另一条流或跳过持久化、顺序和广播。

### 5.5 客户端消息读模型

对外 `MessageDto` 至少包含：

~~~json
{
  "messageId": "guid",
  "meetingId": "guid",
  "sequence": 42,
  "author": {
    "participantId": "guid-or-null",
    "kind": "human",
    "displayName": "Alice"
  },
  "content": "请 @分析师 看一下",
  "mentions": [
    {
      "participantId": "guid",
      "displayName": "分析师",
      "startOffset": 2,
      "length": 4
    }
  ],
  "createdAt": "2026-08-31T08:00:00Z"
}
~~~

系统消息的 `author.participantId` 为 `null`，`kind` 为 `system`；系统展示名称和系统代码由服务端固定，不允许客户端伪造。成功消息的 `kind` 使用小写字符串，不输出整数枚举。

## 6. 统一消息追加边界

### 6.1 统一提交命令

所有入口转换为内部 `MessageSubmission`：

- `MeetingId`；
- 已解析的作者身份来源，即当前人类 `UserId`、绑定 Agent 参与者或系统内部身份；
- `Content`；
- `ClientSubmissionId` 或内部幂等键；
- `Source`，即浏览器、MCP、系统等内部来源元数据。

客户端不得提交 `AuthorParticipantId`、`AuthorKind`、`Sequence`、`CreatedAtUtc` 或 `MessageId` 作为事实。服务端根据认证上下文或受信连接会话解析作者身份。

### 6.2 追加事务

`IMessageAppendService` 的一次追加必须按以下顺序完成：

1. 通过统一会议访问屏障确认会议仍为 `Active`，并确认入口身份属于该会议。
2. 对非空正文执行 NFC+Trim，得到用于幂等比较的规范化正文；此步只做空值/空白校验，不在命中幂等记录前执行最大长度拒绝。
3. 查询幂等键；若已存在成功消息，使用规范化正文按 `StringComparison.Ordinal` 比较，相同返回原消息，不同返回 `SubmissionMismatch`；幂等未命中后才执行最大长度校验。
4. 在同一写事务中分配该会议的下一个 `Sequence`，创建消息作者快照并解析提及。
5. 同事务保存消息、`MessageMention` 和 `MessageAppendedEvent`，提交一次。
6. 提交成功后唤醒事件分发器；事件处理器异步广播或创建后续从属状态。

消息追加必须使用目录 004 的 `IMeetingTransactionRunner` 或与其等价的同连接事务边界。追加服务不得在 Controller、Hub 或未来 MCP Handler 中各自开启事务。

### 6.3 顺序和并发

- 同一会议的所有消息使用同一个顺序分配点，多个参与者并发发送时每条成功消息都得到唯一 `Sequence`。
- 服务端顺序是事务提交前确定的会议顺序，不使用客户端时间、网络到达时间或显示名称排序。
- SQLite 当前在 `BEGIN IMMEDIATE` 写事务中按 `MAX(Sequence) + 1` 分配；`(MeetingId, Sequence)` 唯一索引是最终防线，未来更换数据库时由消息仓储替换分配策略。
- 人类发送和 AI 回复共用同一分配点；外部 AI 处理延迟不能阻塞人类继续发送。
- 顺序冲突或幂等冲突必须转换为稳定业务结果，不把 SQLite 索引名返回给客户端。

### 6.4 发送失败语义

HTTP 发送入口至少区分未认证、非成员或会议不可访问、正文校验失败、发送限流、幂等重放、瞬时追加冲突和内部错误。无法在本次请求安全收敛的序号/唯一约束竞争返回可用同一 `ClientSubmissionId` 重试的 `409 message_append_conflict`；网络超时不能被客户端当作成功，服务端最终返回原消息或明确失败。由于消息限流位于 Application 之前，同一幂等标识的重试也会先消耗限流配额并可能得到 429；这是首版单实例取舍，客户端保留正文和幂等标识等待窗口或手动重试。

## 7. 历史读取与实时传输

### 7.1 HTTP 入口

固定提供以下业务入口，具体 Controller、DTO 和 OpenAPI 响应由 Server 子文档冻结：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| `GET` | `/api/meetings/{meetingId}/messages` | 按会议顺序读取历史或增量消息 |
| `POST` | `/api/meetings/{meetingId}/messages` | 通过统一追加服务发送文本消息 |

历史请求使用 `beforeSequence` 或 `afterSequence`、可选 `throughSequence` 和 `limit` 的游标方式；同一请求不能同时使用两个方向。`throughSequence` 冻结本次追平的服务端高水位，避免活跃会议不断新增消息导致补齐范围漂移。响应返回 `items`、`hasMoreBefore`、`hasMoreAfter`、`firstSequence`、`lastSequence` 和两个方向的下一游标；不得用一个 hasMore 同时表达两个方向。客户端首次进入会议时读取高水位以内的最新一页；空页将实时基线和已应用序号都设为 0，非空页把 `firstSequence - 1` 记录为“更早历史尚未加载”的基线。实时连续性只从该基线向高水位判断，不把未加载的更早消息误判为实时缺口。更早历史通过 `beforeSequence` 按需分批加载。

普通成员可以读取消息历史；会议删除屏障建立后历史、增量和发送均返回 `404 meeting_not_found` 或统一不可访问结果，不泄露会议仍在清理中的状态。

### 7.2 浏览器实时通道

浏览器实时接收使用 ASP.NET Core SignalR Hub 适配器。Hub 只负责连接认证、会议组订阅、事件推送和连接生命周期，不直接修改消息表；本主题浏览器发送固定使用可幂等重试的 HTTP 入口。未来若开放 Hub 发送命令，也必须委托 `IMessageAppendService`。

每个连接加入会议组前必须检查 Cookie 认证、当前账号参与者关系和删除屏障。服务端事件至少包括：

- `messageAppended`：已提交的完整 `MessageDto`；
- `participantPresenceChanged`：参与者标识、`online | offline` 状态和服务端时间；该契约不区分浏览器或 MCP 连接来源；
- `meetingDeleted`：会议已不可访问，客户端应停止订阅并回到无选择工作台。

事件只在消息事务提交成功后发送。重复事件是允许的，客户端必须按 `messageId` 去重并按 `sequence` 排序；事件丢失或连接断开由历史接口补齐。

### 7.3 刷新、断网和重连

客户端保存当前内存中的 `earliestLoadedSequence` 和连续追平后的 `lastAppliedSequence`，不把它们当作跨设备已读状态。连接建立或重建时按以下顺序恢复：

1. 以当前 `meetingId` 建立认证 Hub 连接并开始缓冲事件。
2. 订阅会议组并取得本次 `highWatermarkSequence` 与 presence 快照。
3. 首次进入时读取 `throughSequence = highWatermarkSequence` 的最新一页；已有历史时使用 `afterSequence = lastAppliedSequence` 和同一高水位分批补齐。
4. 将高水位以内的历史与高水位之后缓冲的事件合并，按 `sequence` 排序并按 `messageId` 去重；连续性检查从首屏已加载页的 `firstSequence - 1` 基线开始，只有该实时段内部存在缺口时才继续用历史接口补齐，不跳过缺口推进 `lastAppliedSequence`。
5. 更早历史通过 `beforeSequence = earliestLoadedSequence` 按需加载；追平后显示已连接状态。
6. 若收到删除事件或历史接口返回不可访问，关闭连接、清理当前会议消息并回到无选择状态。

先订阅并取得高水位再补齐，可以避免“查询完成后、订阅建立前”的消息空洞，也避免持续活跃会议使补齐永远追不上。订阅期间收到的重复消息由稳定消息 ID 和序号合并，不要求 SignalR 提供恰好一次投递。

## 8. @ 提及规则与后续处理扩展

### 8.1 服务端解析

消息正文中的 `@参与者名称` 由服务端依据当前会议参与者快照解析，使用目录 004 统一的 NFC + `ToUpperInvariant()` + `StringComparison.Ordinal` 比较规则。`@` 必须紧邻完整显示名称；服务端在当前位置对参与者名称执行最长匹配，名称后必须到达正文末尾或空白、标点边界。无法唯一匹配的 `@` 文本保留为普通正文，不产生提及记录。

客户端提及选择器可以随发送请求提交 `participantId + startOffset + length` 候选，改善包含空格或标点名称的输入可靠性；服务端必须重新验证目标属于当前会议、范围合法，并且正文范围等于 `@` 加目标显示名称。没有候选元数据的 MCP 或系统入口仍使用服务端解析器。客户端候选不能替代服务端授权和名称校验。

解析结果保存 `TargetParticipantId`，因此参与者显示名称未来即使允许扩展，也不会让历史处理失去目标身份。单条消息中重复出现同一目标时保留每一个合法且不重叠的范围；后续业务处理按 TargetParticipantId 去重，多目标消息保留各自出现记录。

### 8.2 发送者类型与处理器

人类和 AI 作者的消息都可产生通用提及记录；系统消息不产生可触发 AI 的提及记录。消息追加事件对所有作者类型保持同一格式，后续 AI 主题可以按 `AuthorKind = human | agent` 和目标参与者类型筛选，创建自己的回复任务。

本主题不等待、不调用外部 Agent，也不因存在 `@AI` 就改变消息发送成功语义。后续 AI 主题必须通过持久化事件消费者保证消息保存和任务创建之间最终不丢失，并使用独立消费确认与幂等约束；不能依赖一次进程内回调。

## 9. 参与者在线状态

在线状态是连接层派生状态，不改变目录 004 的长期参与关系，也不写入消息作者身份。

- Presence 契约统一引用 `ParticipantId`；本阶段由人类浏览器连接注册，后续 MCP Agent 连接复用同一在线状态契约，而 Agent 的 waiting/processing 属于额外处理状态。
- 同一参与者可以有多个受信连接；从 0 条活动连接变为 1 条时广播 `online`，从 1 条变为 0 条并经过短暂断线宽限期后广播 `offline`。
- SignalR 心跳、断开回调和服务端超时共同决定连接是否仍然活动；关闭页面不删除参与者。
- 当前主题的在线状态保存在进程内连接注册表中，服务端重启后所有人先视为离线，重新连接后再广播在线；首版单实例部署不引入跨节点 backplane。
- 在线状态不是未读、已读或 AI 处理状态。未来 AI 主题可在同一参与者列表上增加 `waiting | processing | disconnected` 等处理状态，但不能把这些状态写入消息历史。

本主题提供系统消息追加能力，但不把每次网络抖动都永久写成聊天记录，也不在 004 会议创建/加入事务之外隐式补写“已加入”系统消息。普通上线、离线和重连只通过 presence 实时事件表达。后续主题若需要持久化系统事实，必须明确 occurrence key，并通过产生该事实的同一事务登记消息或领域事件，不能在本主题请求之后另开嵌套事务。

## 10. 权限、安全与删除闭环

### 10.1 权限

1. 浏览器历史和发送 API 必须使用目录 003 的 Cookie 认证。
2. 只有当前账号属于该会议的人类参与者，才能通过 HTTP 或 SignalR 读取消息和在线状态。
3. HTTP 入口根据当前用户上下文解析作者参与者；客户端提交的参与者 ID、作者类型和创建时间全部忽略。
4. 系统消息只能由受信服务端用例创建；未来 Agent 入口只能使用绑定的 Agent 参与者和连接会话身份。
5. 不同会议的消息查询、Hub 组和事件缓存必须按 `MeetingId` 隔离。

对非成员请求继续沿用目录 004 的 `404 meeting_not_found` 语义，不泄露会议存在性。

### 10.2 输入和防护

- 正文先做 NFC 规范化和首尾空白处理；空正文拒绝，长度上限由配置校验并在服务端执行，首版默认上限为 16,384 个 UTF-16 代码单元。
- 消息正文、显示名称和提及范围不得进入日志模板中的完整请求体；日志只记录会议 ID、参与者 ID、消息 ID、序号、结果和 traceId 等必要摘要。
- 所有消息 API 使用 `no-store` 约束；会议码、Cookie 和密码不得出现在消息 URL、事件载荷、异常或日志中。
- 发送入口提供按账号、参与者和来源地址的配置限流；限流失败不能消耗顺序号，也不能写入半条消息。
- 客户端按文本渲染正文，不使用不可信 HTML；提及高亮通过已验证范围切分文本，不通过 `dangerouslySetInnerHTML`。

### 10.3 删除闭环

会议从 `Active` 原子转为 `Deleting` 后：

1. 历史、增量、发送和 Hub 加入立即拒绝。
2. 已连接客户端收到 `meetingDeleted` 后关闭订阅并清理内存消息。
3. 删除状态转换与消息广播通过同一个会议级实时 gate 串行化：独占请求先原子进入 `Closing` 中间态并立即拒绝新的共享租约，只等待已经持有的短租约归还；订阅连接不在连接存续期持有共享租约。独占等待有配置上限，超时释放 `Closing`、会议保持 `Active` 并返回可重试错误；独占成立后才提交 `Deleting` 屏障，提交失败释放租约，提交成功将租约转为永久关闭并发送 `meetingDeleted`。
4. 删除协调器终止本主题登记的 Hub 组，再在数据库事务中删除消息事件消费状态、`MessageMention`、`MeetingMessage` 和会议工作台已有从属数据。
5. 清理失败时保持 `Deleting`，重启后继续；不能恢复会议访问，也不能只删除部分消息。
6. 删除成功后旧消息 ID、会议 ID 和旧连接都不能继续读取或发送。

后续 AI 主题增加任务、连接和上下文游标时，必须把它们登记到同一删除协调器，并在删除回归中验证 AI 处理器不会再次创建消息。

## 11. 客户端工作台方向

本主题在会议工作台主题的消息区插槽中接入真实消息体验，保留会议导航、详情和参与者身份边界。页面不把消息区做成独立会议或独立连接入口。

### 11.1 页面结构

- `MeetingWorkspacePage` 继续拥有当前会议选择、删除后的回退和主题级错误提示。
- `MessageTimeline` 展示按 `sequence` 排序的消息、作者显示名称、作者类型、时间、提及高亮和系统消息样式。
- `MessageComposer` 负责正文编辑、参与者提及选择、发送中或失败状态和重试。
- `ParticipantList` 增加人类参与者在线和离线状态，但不修改参与者长期身份或显示名称。
- 连接状态以页面级状态提示呈现；不能用一个消息气泡假装实时连接已恢复。

### 11.2 客户端状态

`meetingWorkspace` feature 扩展维护：

- 当前 `meetingId` 对应的消息 Map、按序号排列的可见序列和 `lastAppliedSequence`；
- 历史加载游标、是否还有更多、首次加载、增量加载和重连状态；
- SignalR 连接状态、客户端本地 connection generation 和 Abort/Dispose 资源；
- 当前会议参与者的 presence 快照；
- Composer 草稿、当前 `ClientSubmissionId`、发送中和失败可重试状态。

路由切换、删除、注销或组件卸载时必须关闭旧 Hub、取消历史请求、清理旧会议消息和 presence，旧会议的迟到事件不能写入新会议状态。

### 11.3 交互约束

- 发送成功以后以服务端 `MessageDto` 为准渲染，不以客户端时间或临时序号覆盖服务端顺序。
- 网络失败保留草稿和同一幂等标识，用户可以重试；明确的校验或权限错误不自动重复提交。
- `@` 选择器显示当前会议参与者，并在发送前保留原始文本；未知 `@` 文本不阻止发送。
- 系统消息、AI 预留作者类型和人类消息必须在视觉上有文字类型标记，不能只依赖颜色。
- 首版不显示未读数量、不在本地持久化历史消息、不把会议码或消息正文写入 URL。

## 13. 前置与后续主题依赖

本主题依赖目录 003 的 Cookie 认证、当前用户上下文和统一错误或 Origin 边界，依赖目录 004 的 `MeetingId`、`ParticipantId`、参与者类型、显示名称唯一性、成员授权、工作台路由和删除访问屏障。

总体计划主题五“AI 参会”依赖本主题输出的：

1. 统一 `MeetingMessage`、`MessageMention` 和 `MessageDto` 契约。
2. 统一 `IMessageAppendService` 和消息追加事务边界。
3. 历史读取、按 `Sequence` 增量补齐和稳定消息标识。
4. 持久化 `MessageAppendedEvent` 及可插拔的独立消费者边界。
5. 参与者类型兼容值固定为 `human | agent`；消息作者类型兼容值固定为 `human | agent | system`，`system` 不属于参与者类型。
6. 会议删除后消息不可读、不可写、不可广播的事实。

后续 AI 主题可以增加 Agent 连接、上下文游标、回复任务和 MCP 发送适配，但不能：

- 另建 `AgentMessage` 或 AI 专用历史接口；
- 直接修改 `MeetingMessages` 表绕过追加服务；
- 用 AI 任务状态替代消息的持久化状态；
- 将 AI 的处理状态写入消息作者或消息顺序字段。

## 14. 完成门槛

本主题只有在以下结果全部成立时才算完成：

- 两个已登录账号在同一会议中可以通过真实浏览器发送和实时接收文本消息。
- 消息、系统消息和后续 Agent 消息在同一模型、同一 `Sequence` 顺序流和同一历史接口中表达；当前阶段验证人类消息和受信系统追加契约，但不自动从会议加入流程生成系统消息。
- 并发发送不会覆盖消息；所有客户端最终按服务端顺序显示。
- 发送成功后先持久化再广播；广播丢失、刷新或短暂断网后可以通过 `afterSequence` 补齐，重复事件不会重复显示。
- 同一客户端重试使用相同幂等标识不会创建第二条消息；发送失败不会显示成已发送。
- `@` 参与者名称可以解析为稳定参与者 ID，同一目标重复提及的每个文本范围均可高亮，而后续任务目标按 ParticipantId 去重；多目标提及均保留，系统消息不产生可触发 AI 的提及。
- 历史消息只属于当前会议，切换会议和刷新不会串线，也不把消息写入 URL 或持久化浏览器存储。
- 当前会议人类参与者的在线和离线变化可见，关闭页面或断线不删除参与关系；服务端重启后的在线状态按重新连接恢复。
- 非成员、未认证、Deleting 会议和跨会议访问都经过统一授权或删除屏障，错误不泄露会议存在性。
- 删除会议后消息、提及、实时订阅和连接都不可继续访问；删除清理失败或服务重启不会重新开放会议。
- 后续 AI 主题可以只增加入口适配和处理器，不需要改造消息核心或建立平行消息流。
- 本主题没有提前实现 MCP、AI 回复任务、上下文裁剪、接管、循环保护或未读状态。

实现步骤和测试矩阵在本主题设计审阅通过后分别编写到 `impl.md` 和 `testPlan.md`；子文档不能借实现细节扩展本主题范围。
