# 圆桌会议网站总体设计

## 1. 文档目的

本文只确定圆桌会议网站第一版的总体方向、系统边界、实施主题划分、主题依赖和实施顺序。

具体的技术栈、工程分层、项目结构、依赖包、数据表字段、接口定义、页面交互、消息提及算法、AI 任务状态机、上下文裁剪算法、并发控制和测试用例，由系统框架或对应业务主题的设计文档负责。总体计划只固化跨主题产品契约、系统边界和实施方向，不提前替代主题详细设计。

产品需求以[圆桌会议网站需求](../../需求分析/圆桌会议网站需求.md)为准。`Demo/驻留参与者协作实验`只作为 MCP 驻留参与模式的技术可行性参考，不作为正式系统结构。

## 2. 总体目标

第一版需要验证：多个人类用户和多个外部 AI Agent，能否通过会议码加入多个相互隔离、长期存在的群聊，并在同一条消息流中通过 `@` 自然协作。

系统围绕以下能力建设：

1. 人类账号登录和最小身份接入。
2. 多个会议的创建、加入、切换和删除。
3. 人类与 AI 共用的持久化群聊消息流。
4. 外部 AI Agent 通过 MCP 加入，并在被明确 `@` 时获得上下文和回复任务。
5. 浏览器刷新、Agent 断线和服务端重启后的状态恢复。

第一版保持自由群聊定位，不引入主持、议程、会议总结、AI 主动发言、未读状态和复杂权限。

## 3. 总体架构方向

### 3.1 系统形态

第一版采用模块化单体架构，以较低的部署和开发复杂度完成产品逻辑验证。

- 服务端统一承载 Web API、浏览器实时通信、MCP 接入、业务服务和后台任务。
- 客户端采用独立 Web 应用。
- 数据库统一持久化账号、会议、参与者、消息和 AI 协作状态。
- 浏览器连接、MCP 等待连接和内存通知只作为通信手段，不能成为唯一数据来源。

### 3.2 系统框架方向

第一版先建立独立的系统框架主题，集中确定并验证服务端、客户端、数据库和测试工程的技术基础。该主题负责选定具体技术栈、工程分层、项目结构、依赖方向、基础配置和开发运行方式；总体计划不重复保存这些可由框架主题独立演进的实施细节。

系统框架必须满足以下跨主题方向：

- 客户端、服务端和数据库能够集成启动，并提供可见的浏览器验收入口。
- 服务端入口、业务编排、领域规则和基础设施职责有明确边界，具体分层及是否引入仓储抽象由系统框架主题结合项目需要决定。
- 数据库是账号、会议、参与者、消息和 AI 协作状态的持久化事实来源。
- 浏览器实时连接、MCP 等待连接和进程内通知只承担通信职责，不能替代持久化状态。
- 可恢复的异步工作由持久化状态和后台执行机制共同完成。
- 长连接和等待操作必须支持异步、取消、超时和资源释放，不以每个连接永久占用线程为前提。
- 各业务入口必须复用统一的数据访问、事务、错误处理和可观测性边界，不能绕过框架约束各自实现。

框架主题只搭建后续业务共同需要的基础能力，不提前实现认证、会议、实时群聊或 AI 协作等业务功能。相关专项技术在最早使用它的业务主题中完成集成和验收。

## 4. 核心系统边界

### 4.1 身份边界

系统必须区分三种生命周期不同的身份：

- 人类账号：平台范围内的登录身份。
- 会议参与者：人类或 AI 在某个会议中的长期身份和固定显示名称。
- AI 连接会话：某个外部 Agent 当前接入会议的临时连接实例。

AI 断线和接管只替换连接会话，不创建新的同名会议参与者。人类重新打开会议时根据账号恢复原参与者。

### 4.2 会议边界

会议是参与者、消息和 AI 协作状态的隔离边界。不同会议之间不得共享消息、参与者身份、连接状态或 AI 待处理任务。

会议长期存在，没有正式的开始和结束状态。只有创建者可以删除会议；删除开始后，系统必须先阻止新的访问和写入，再完成关联数据及连接的清理。

会议删除采用分阶段收敛：主题三提供创建者可见且可用的基础删除能力和统一访问屏障；后续主题引入新的会议从属数据、连接或后台任务时，必须同步将其纳入已有删除闭环；主题七负责完成连接终止、未完成任务处理、服务端重启后的可重入清理和第一版最终验收。

### 4.3 消息边界

人类消息、AI 消息和系统消息进入同一条由服务端排序的持久化消息流。人类和 AI 不能使用相互独立的消息通道。

消息保存、有效 `@` 提及识别和 AI 回复任务创建必须保持一致，不能出现消息已保存但任务永久丢失的情况。

### 4.4 AI 协作边界

首版 AI 只在被明确 `@` 时参与。人类消息和 AI 消息都可以触发目标 AI，系统消息不触发 AI。

每次有效提及都形成独立、持久化的回复任务。任务需要支持排队、失败恢复、连接接管和回复幂等；具体状态和重试机制由 AI 协作主题设计。

AI 加入时声明当前连接可接受的上下文字符数。服务端向它提供最近的连续上下文，并在后续任务中包含从上次上下文位置到触发消息之间的全部连续消息。上下文必须包含人类、AI 和系统消息，触发消息不能因裁剪而丢失。

AI 消息可以继续 `@` 其他 AI，服务端保留任务触发来源以支持追踪。协作是否完成由参与的 Agent 和用户判断；网站不按协作轮数、深度或累计任务数自动截断，也不提供暂停入口。需要停止执行时，由人类直接操作对应 Agent 的外部工具。

对外 MCP 交互必须使用稳定的消息标识、任务标识和投递尝试标识。消息重投、任务重试和 AI 识别自己已经处理过的消息都依赖这些标识；上下文被裁剪时还必须提供候选范围、实际范围和裁剪信息等稳定的协议元数据。具体字段格式由 AI 协作主题确定，但不能在不同主题或不同入口中各自定义。

## 5. 逻辑模块

总体上划分为以下逻辑模块：

1. 账号与身份模块：第一版先负责人类登录和平台身份，完整账号管理在核心业务验证完成后再扩展。
2. 会议与参与者模块：负责会议生命周期、会议码、会议内身份和参与状态。
3. 群聊消息模块：负责统一消息流、历史读取、提及和浏览器实时同步。
4. MCP Agent 与 AI 协作模块：负责 Agent 接入、上下文、回复任务、接管和恢复。
5. 基础设施模块：负责数据持久化、认证、后台任务、实时连接和通用错误处理。

业务模块通过应用服务协作。Web API、浏览器实时通信和 MCP 只作为入口层，不在入口中直接实现核心业务规则。

以上是系统内部的逻辑模块，不等同于实施主题。实施主题按用户可完成的业务流程垂直拆分，每个主题可以同时修改多个逻辑模块。

## 6. Web 客户端方向

客户端第一版采用登录后直接进入工作台的结构：

- 左侧展示用户创建或曾经加入的会议，并提供创建会议和通过会议码加入的入口。
- 右侧展示当前会议的基本信息、完整消息历史、参与者状态和消息输入区。
- 用户可以在同一页面快速切换多个会议。
- 页面刷新或实时连接恢复后，以服务端数据为准恢复当前状态。
- 首版不显示未读数量、已读位置和跨设备通知。

页面组成、响应式布局、交互状态和组件边界在各主题的 Client 设计中确定。

## 7. 实施主题拆分

系统框架完成后，业务主题按照可独立演示和验收的用户能力垂直拆分，而不是按照 Client、Server、数据库或基础设施横向拆分。完成一个业务主题后，开发者和验收人员必须能从浏览器界面看到新的完整业务能力；涉及外部 Agent 的主题还需要同时提供可执行的 MCP 联调路径。

系统框架是业务主题之前唯一独立设置的技术基础主题，但它同样必须提供可见、可运行、可自动验证的集成结果，不能只交付目录和依赖清单。后续通用基础设施随最早使用它的业务主题扩展，不再建立脱离业务闭环的横向技术主题。

每个业务主题都应包含实现该业务闭环所需的客户端、服务端、持久化、自动化测试和手工验收说明。

本阶段确定以下七个实施主题，但不提前创建尚未进入设计的主题目录。

### 7.1 主题一：系统框架设计

建设目标：建立后续业务主题共同依赖的可运行工程基础，并通过真实的前后端和数据库集成证明框架可用。

范围包括具体技术栈和版本策略、服务端分层及依赖方向、客户端工程结构、数据库与迁移基础、配置与环境约定、统一异常和错误响应、日志与基础可观测性、前后端联调方式、构建测试工具链及最小应用外壳。该主题只提供框架级能力和验证入口，不提前实现账号、会议、消息或 AI 业务。

可见验收结果：开发者能够按文档启动客户端和服务端；浏览器打开最小应用外壳后，能够通过真实服务端接口显示应用与数据库处于可用状态；服务不可用时页面显示明确失败状态；客户端和服务端均可完成构建、自动化测试和基础分层约束检查。

### 7.2 主题二：账号访问与用户管理

业务目标：提供稳定的人类登录身份、管理员专属的账号管理，以及所有用户可使用的个人设置。

本主题包括初始账号与管理员初始化、用户名密码登录、退出、刷新保持登录、当前账号资料和统一认证边界。管理员可以查看用户列表、添加账号、修改昵称、固定重置密码，以及设置或取消管理员身份；系统至少保留一名管理员。普通用户不能进入用户管理页面或调用管理接口。所有用户可以在个人设置查看账号信息、修改自己的昵称和密码。

账号管理权限与会议权限独立：管理员不因此获得其他会议的访问或删除权限。昵称修改不覆盖已有会议显示名称。密码使用不可逆哈希，重置值固定为 `123456`；密码和 Cookie 不进入日志。管理员撤销对后续管理请求生效，密码修改与重置沿用已有会话有效期，不主动撤销会话。

本主题不包括搜索分页、修改用户名、账号禁用或删除、复杂角色组织权限、账号审计、自助找回、多因素认证和高级会话管理。具体初始化、并发保护、接口及页面方案由 003 主题负责。

可见验收结果：管理员和普通用户都能登录并使用个人设置；普通用户无法查看账号目录或管理他人；管理员可以添加账号、固定重置密码和调整管理员身份；最后一名管理员不能被取消；管理员撤销后旧登录不能继续执行管理操作；后续主题继续从统一身份上下文取得稳定用户标识。

### 7.3 主题三：会议工作台

业务目标：让已登录用户可以建立和管理多个长期存在的群聊空间。

范围包括工作台基本布局、会议创建、会议码、会议列表、通过会议码加入、会议内固定显示名称、名称唯一性、参与者静态身份与基础列表、多个会议切换、原参与身份恢复，以及创建者可用的基础会议删除能力和统一删除访问屏障。该主题设计需要明确会议码安全随机强度、防刷取执行点、日志脱敏和成员访问授权的验证方式。该阶段只需要删除当时已经存在的会议从属数据；后续主题必须扩展同一删除闭环。

可见验收结果：用户可以创建会议并看到会议码；另一个账号可以使用会议码和自己的会议昵称加入；双方能在参与者列表中看到彼此；用户可以创建或加入多个会议并从左侧列表切换；刷新后会议仍在；创建者可以删除会议，会议从列表中消失，会议码不再能够恢复该会议。

### 7.4 主题四：实时群聊

业务目标：建立面向所有会议参与者的统一、持久、实时文本消息流，并先通过浏览器完成人类参与者的可见闭环。人类和 AI 都是同一参与者模型中的消息发送者；两者只在接入方式、身份校验方式和收到消息后的处理方式上存在差异。

范围包括统一参与者消息模型、文本发送、完整历史、服务端消息顺序、并发消息追加、系统消息、`@参与者` 解析与提及记录、浏览器实时广播、发送失败反馈、参与者在线和离线状态，以及浏览器刷新和实时连接重建后的消息恢复。该主题负责统一消息追加边界，浏览器 HTTP 入口、后续 MCP 入口和后台处理器都不能绕过这一消息顺序入口；负责参与者在线/离线状态及其实时变化，不重新定义会议主题的参与者身份；同时扩展会议删除闭环，使消息、提及记录和浏览器实时状态不会在删除后继续可见或可写入。

可见验收结果：两个浏览器中的不同账号进入同一会议后可以实时互发消息、看到一致顺序和历史；刷新或短暂断网后不会丢失或重复显示已经保存的消息；用户可以从参与者列表选择并输入 `@参与者`；用户分别在会议 A 和会议 B 中发送消息时，切换会议后只能看到当前会议的消息、参与者和在线状态，两个会议的历史和实时广播不会串线；删除包含消息的会议后，消息历史和浏览器实时订阅都不可继续访问。

### 7.5 主题五：AI 参会

业务目标：让外部 AI Agent 能够作为正式参与者加入现有会议，获得必要的聊天上下文，在被明确 `@` 时处理讨论内容并将回复发布到统一消息流。

范围包括 MCP 接入、使用会议码和显示名称加入、连接会话、上下文字符数协商、最近初始上下文、驻留参与指令、持久化提及任务、每个 AI 各自任务的基本 FIFO 排队、连续任务上下文、字符数裁剪、等待提及任务、AI 回复提交，以及网页中的 AI 参与者、连接状态和回复展示。同一会议允许多个 AI 分别建立独立参与者身份、连接会话、上下文游标和任务队列；本主题以一个 AI 正常参会和回复作为最低验收场景，不在此阶段解决多个 AI 之间的协作链、租约、断线接管、服务重启恢复和复杂异常恢复。同时把 AI 连接和基础任务纳入已有会议删除闭环。本主题需要统一确定 MCP 能力和字段草案，后续 AI 主题在保持兼容的前提下扩展。MCP 联调需要提供可实际运行的最小参考 Agent 或测试客户端，具体落地位置在该主题设计中确定。

可见验收结果：外部 Agent 通过 MCP 加入后出现在网页参与者列表中；人类发送包含 `@AI名称` 的消息后，Agent 能得到从上次上下文位置到触发消息之间的全部连续消息，并按自身字符数获得最近上下文后回复；回复实时出现在所有在线用户的共享消息流中；未被 `@` 时 Agent 保持等待，不主动发言；同一 AI 在上一条任务处理期间收到多条 `@` 时，任务按消息顺序排队并逐条回复，不覆盖或丢失任务；删除包含 AI 连接和基础任务的会议后，网页和 Agent 都不能继续访问或回复该会议。

### 7.6 主题六：AI 任务连续性与接管

业务目标：让单个 AI 在连续提及、断线、替换和服务端重启情况下仍能可靠完成回复任务。

范围包括在 AI 参会主题基础上的持久化回复任务连续性、上下文进度、字符数裁剪和裁剪说明、任务确认、回复幂等、失败重试、连接租约、临时断线后的原连接恢复、使用原名称接管原 AI 参与者、迟到回复隔离，以及服务端重启恢复。临时断线恢复和新 Agent 接管必须保持不同语义：前者可以保留原连接会话配置，后者建立新连接会话并重新声明上下文字符数。本主题继续扩展会议删除闭环，覆盖新增的 AI 任务、租约和连接恢复状态。

可见验收结果：同一 AI 连续收到多个提及时按消息顺序回复；处理过程中断开后，页面能显示状态变化，原 Agent 重连或新 Agent 接管后可以继续未完成任务且不产生第二个同名参与者；重复提交不会产生重复消息；服务端重启后待处理任务仍能继续；删除含有未完成 AI 任务和连接恢复状态的会议后，这些任务和连接不能再次恢复。

### 7.7 主题七：多 Agent 协作与会议删除收口

业务目标：让多个 AI 能够在群聊中相互 `@` 并形成可观察、可控制的协作过程。

范围包括 AI 消息触发其他 AI、多个目标 AI 的独立任务、用于来源追踪的协作链标识，以及会议删除闭环的最终可靠性建设。该主题负责补全创建者删除会议时对全部会议关联数据、AI 连接和未完成任务的终止与清理，并确保删除流程具有持久化删除中状态、可重入清理和服务端重启后的继续执行能力。本主题不再首次引入删除能力，而是完成第一版发布前的删除可靠性收口，不可被省略。

可见验收结果：一个 AI 可以通过 `@` 组织另一个 AI 回复，多个 Agent 的协作过程完整显示在群聊中；不同 AI 根据各自上下文获得独立任务；多轮相互提及不会因轮数或次数被平台截断，Agent 和用户自行决定是否继续；创建者删除会议后，会议从相关列表中消失，消息、参与者、AI 任务和连接均不可继续访问，旧会议码也不能恢复会议；服务端在删除过程中的重启不会使会议重新可访问，清理可以继续完成；其他会议仍可继续由人类正常聊天。

## 8. 主题依赖与完成标准

主题按照一条逐步扩展的可运行产品链路实施：

1. 系统框架设计建立可运行、可测试的客户端、服务端和数据库基础。
2. 账号访问与用户管理提供后续主题不可缺少的最小登录身份，以及内部测试所需的四项极简账号维护能力；不等同于完整用户中心。
3. 会议工作台建立多人空间。
4. 实时群聊让会议具备统一的参与者交流能力，并先完成浏览器人类参与者闭环。
5. AI 参会使外部 Agent 能够加入会议、获得上下文并在被明确 `@` 时参与讨论，同时覆盖每个 AI 的正常任务排队。
6. AI 任务连续性与接管使最小闭环具备可靠恢复能力。
7. 多 Agent 协作与会议删除收口完成第一版的多 Agent 协作和会议生命周期目标。

后续主题可以扩展前面主题的数据模型、界面和服务，但必须保持已有业务路径继续可用。引入新的会议从属数据、连接或后台任务时，必须同步登记其归属并扩展已有会议删除闭环，回归验证删除后不可读取、不可写入、不可恢复。会议工作台完成后已经具备基础可用的会议删除能力；实时群聊至 AI 任务连续性与接管持续覆盖新增资源；只有多 Agent 协作与会议删除收口完成后，第一版的删除并发、连接终止和崩溃恢复语义才全部收口。各主题的 `testPlan.md` 必须明确本主题新增资源对应的删除回归范围，以及与完整删除闭环之间的关系。客户端业务功能随对应主题一起设计和实现，不再建立脱离业务闭环的横向客户端主题。

一个主题只有同时满足以下条件才视为完成：

- 系统框架主题能够从浏览器观察真实集成状态，并通过构建、测试和分层约束检查。
- 业务主题能够由用户从浏览器界面完成其声明的主要业务流程。
- 涉及 AI 时，提供可以实际运行的 MCP 联调流程，并且结果能在网页中观察。
- 客户端、服务端和持久化能力已经集成，不以模拟数据替代最终业务闭环。
- testPlan.md 中的自动化测试和手工 UI 验收场景通过。
- 前面已经完成的主题仍能通过其核心回归场景。

## 9. 跨主题不变约束

后续主题设计不得改变以下已经确认的产品约束：

1. 同一会议内人类和 AI 的显示名称统一唯一，首次加入后固定。
2. 账号昵称是账号资料；用户管理阶段的昵称修改只更新账号资料，会议内显示名称及其是否影响既有参与关系由会议主题定义。
3. 人类账号与会议参与者身份分离，AI 参与者与连接会话分离。
4. 同一会议中的人类、AI 和系统消息共享一条服务端顺序流，所有入口都通过统一消息追加边界。
5. 每条对外投递消息必须带稳定消息标识；每次 AI 回复任务必须带稳定任务标识、投递尝试标识和可用于幂等处理的标识。
6. 人类和 AI 消息中的 `@AI` 都能产生回复任务，系统消息不能。
7. AI 回复任务状态与上下文投递进度分离，任务不能仅由游标推断；上下文成功投递后即可推进投递进度，不等待 AI 回复，但已投递未回复的任务仍须独立保留；必要的任务和上下文进度必须持久化。
8. 上下文按连接声明的字符数提供，包含其他 AI 消息，不分页补发被裁剪的旧消息；裁剪结果必须通过稳定协议元数据说明。
9. 新 Agent 使用会议码和原 AI 显示名称接管原参与者，接管后旧连接失效；临时断线恢复与新连接接管是两种不同的恢复语义。
10. 同一会议内名称比较必须使用统一的去除首尾空格、Unicode NFC 规范化和不区分大小写规则，规范化后为空的名称不能加入。
11. 消息和参与关系长期保留，直到会议被创建者删除。
12. 多个会议必须相互隔离，并支持在同一页面内切换。
13. 只有已登录且属于会议参与者的人类账号可以读取会议内容；AI 连接只能访问其绑定的会议和参与者范围。
14. 人类必须登录后访问，密码必须以不可逆哈希保存，日志不得记录密码正文或认证 Cookie；会议码应使用不可预测的安全随机值并具备防猜测、防刷取和日志脱敏措施。
15. 会议删除能力从会议工作台主题开始提供；后续主题引入的会议从属数据、连接和后台任务必须纳入同一删除闭环，并通过删除回归场景验证。
16. 所有会议读取、写入、回复和接管入口都必须先经过统一删除访问屏障检查；会议删除开始后这些入口必须拒绝操作，删除过程必须能够在服务端重启后继续完成。
17. 平台不判断协作完成条件，不做业务循环截断或暂停入口；人类在外部 Agent 工具中停止执行。外部停止不删除参与者或未完成任务，平台按真实连接状态与既有恢复规则处理。

## 10. 推荐实施顺序

1. 系统框架设计，建立可运行的 Server、Client、数据库和测试工程基础。
2. 账号访问与用户管理。
3. 会议工作台。
4. 实时群聊。
5. AI 参会。
6. AI 任务连续性与接管。
7. 多 Agent 协作与会议删除收口，同时完成删除的并发、连接终止和崩溃恢复闭环。

每个主题先完成 design.md，再形成 impl.md 和 testPlan.md，之后进入该主题的源代码实现和验收。一个主题完成后，主应用应始终保持可启动、可操作和可演示。涉及 MCP 的主题还必须保留可重复执行的参考 Agent 或测试客户端联调路径。

## 11. 总体验收方向

第一版最终需要从整体上证明：

- 人类能够登录、创建和加入多个会议，并在同一页面切换。
- 多个人类和 AI 能够通过唯一显示名称进入同一会议并共享消息历史。
- 人类或 AI `@` 某个 AI 后，目标 AI 能获得合适上下文并可靠回复。
- 多个 AI 可以通过 `@` 持续协作，合法新提及独立排队，技术重试不会重复创建消息或任务。
- 浏览器刷新、Agent 断线、Agent 接管和服务端重启不会破坏已保存消息和未完成任务。
- 创建者删除会议后，会议数据、连接和旧会议码均不可继续访问。

具体可执行验收用例由各实施主题的 `testPlan.md` 定义。总体版本验收由系统框架和六个业务主题的可见路径串联组成，不以单独的接口测试或数据库检查替代浏览器验收。
