# 圆桌会议网站需求

## 1. 产品定位

圆桌会议网站是一个支持人类与外部 AI Agent 共同参与的多人群聊平台。用户创建一个会议后，系统生成会议码；人类参与者通过会议码加入，外部 AI Agent 通过 MCP 使用会议码加入。加入后，所有参与者共享同一条持续存在的消息流。

这里的“会议”不是有主持人、议程、发言顺序和明确结论的正式会议，而是一个可以随时加入、暂时离线、重新回来和继续讨论的群聊房间。参与者不主动退出会议，关闭页面或连接中断只改变在线状态，不改变参与关系。

平台负责提供房间、参与者身份、消息传递、实时状态和会话持久化；人类用户通过账号体系管理自己的会议和参与记录。外部 AI Agent 的角色设定、模型能力、记忆、工作目录以及它产生的外部文件，不属于平台控制范围。

## 2. 产品目标

### 2.1 主要目标

1. 让用户可以低成本创建一个人类和 AI 都能加入的讨论空间。
2. 让多个外部 AI Agent 以相互独立的参与者身份进入同一个群聊。
3. 让人类能够通过自然的群聊方式与指定 AI 或多个参与者交流。
4. 允许多个会议同时存在，用户可以在不同会议之间切换，而不会混淆消息和参与者。
5. 保持消息、参与关系和待处理任务的连续性，使参与者暂时离线或外部 Agent 被替换后会议仍可继续。

### 2.2 非目标

首版不以以下能力为目标：

- 正式会议主持、议程、轮流发言、计时和举手。
- 强制生成会议纪要、结论、投票结果或待办事项。
- 在平台内创建、配置或训练 AI 角色。
- 接管 AI 的记忆、工作目录、文件产物或外部工具执行结果。
- 通过平台内置模型直接替代外部 AI Agent 的接入。
- 音视频通话、屏幕共享和实时语音转写。

## 3. 核心概念

### 3.1 会议

会议是一个独立的群聊房间，具有独立的会议码、参与者列表、消息流和连接状态。会议可以在暂时没有参与者在线时继续保留，后续参与者可以凭会议码重新连接。参与者关系和发言记录长期保留，参与者不主动退出会议。

“开始会议”和“结束会议”不是首版的核心生命周期概念。关闭浏览器、网络断开或所有参与者暂时离线，都不等于退出会议或删除会议。

### 3.2 会议码

会议码是人类和外部 AI Agent 加入会议的主要凭证。登录后的人类用户和持有会议码的外部 AI Agent 都可以申请加入会议。会议码在会议存续期间长期有效，不允许重新生成或更换；只有删除会议后，会议码才失效。因此会议码需要足够难以猜测，并且不应出现在不必要的公开位置。

### 3.3 参与者

参与者分为两类：

- 人类参与者：使用账号登录后，通过网页输入会议码，并使用账号昵称作为本次会议显示名称的默认值；用户可以在加入不同会议时分别自定义显示名称。加入关系会保留，之后可以再次打开会议继续参与。
- AI Agent 参与者：通过 MCP 加入会议，并以自己提供的显示名称出现在参与者列表和消息流中；连接中断或原 Agent 被关闭后，其他 Agent 可以凭相同的会议码和显示名称接管原参与者的会话状态。

平台还可以产生系统消息，例如参与者加入、重新连接或暂时离线。系统消息不属于人类或 AI 的发言。

### 3.4 外部 AI Agent

外部 AI Agent 是运行在平台之外的 Agent。首版平台不负责创建它、设定它的系统提示词或决定它的专业角色。AI 可以在加入前已经具备自己的角色和工作上下文，也可以在群聊中根据人类发言被进一步引导。一次具体的 Agent 连接实例只加入一个会议；不同会议中出现的相同 Agent 名称，视为不同的会话参与者，平台不要求识别它们是否来自同一个外部 Agent。

平台区分“AI 会议内参与者身份”和“外部连接会话”：AI 参与者身份由会议和会议内显示名称确定，连接会话代表某个外部 Agent 当前接入的传输实例。旧连接关闭后，或新 Agent 明确请求替换仍在线的旧连接时，新连接可以使用会议码和显示名称接管原 AI 参与者身份，并继承其上下文投递游标和未完成任务；新连接本身仍然是新的连接会话，并需要重新声明自己的上下文字符数。首版不要求新连接证明自己就是原来的外部进程。人类参与者身份仍由账号和会议共同确定，不能仅凭会议码和显示名称接管。

平台只需要为 AI 提供加入会议、协商上下文字符数、读取按自身能力生成的最近聊天上下文、接收明确提及自己的消息和发送回复的能力。

## 4. 用户角色

### 4.1 会议创建者

创建会议并拥有该会议管理权限的人类用户。创建者自动成为该会议的一个人类参与者。首版不为创建者引入正式主持流程；创建者可以删除自己创建的会议，但不能重新生成会议码，也不提供踢出、禁言等参与者管理能力。

### 4.2 人类参与者

使用账号登录后，通过会议码进入会议、查看消息、发送消息和提及其他参与者的人类用户。人类账号是平台层面的稳定身份，账号具有一个昵称；显示名称是该账号在特定会议中的参与者名称，加入会议时默认使用账号昵称，也可以针对当前会议单独设置。人类参与者没有主动退出会议的操作。

### 4.3 外部 AI Agent

通过 MCP 使用会议码进入会议、协商自身可接受的上下文字符数、读取按自身能力生成的最近讨论上下文、接收明确提及自己的消息，并以自身名称发送发言的外部 Agent。AI 连接中断或原 Agent 被关闭后，可以凭相同的会议码和显示名称重新连接并接管原参与会话。

### 4.4 系统

负责创建会议、生成会议码、维护账号、参与者和消息记录、处理 MCP 接入、广播实时变化、标识连接状态、删除会议并隔离不同会议的数据。

### 4.5 首版账号管理

账号区分普通用户和管理员。只有管理员可以查看用户列表、添加用户、修改其他用户昵称、将密码重置为固定值 `123456`，以及设置或取消管理员身份。新用户默认是普通用户；系统初始化或首次升级时显式指定初始管理员，任何情况下至少保留一名管理员，包括并发取消操作。管理员身份撤销后，后续用户管理请求立即失去权限。管理员身份仅决定账号管理能力，不改变会议成员访问和创建者删除会议等规则。

所有已登录用户都可以使用个人设置，查看自己的用户名、昵称和管理员身份，修改自己的昵称和密码。用户名不可修改。修改密码必须验证当前密码，并输入新密码和确认新密码；管理员重置密码不需要目标用户的当前密码。修改或重置密码沿用现有会话规则，不主动撤销已有登录，不要求首次登录强制改密。首版不引入复杂角色层级、组织权限、邮箱短信找回或管理审计。

## 5. 首版功能需求

### 5.1 人类账号与登录

人类用户需要使用账号体系访问网站。用户登录后，系统应能够识别其账号，并基于账号展示该用户可以访问的会议。首版不提供公开的自助注册入口，由管理员添加新用户；系统部署或初始化时需要预置至少一个可登录的初始账号。

账号体系至少应支持：

- 登录和退出登录。
- 管理员添加新用户，并设置新用户的用户名、昵称和初始密码。
- 为账号设置昵称，并将其作为加入会议时的默认显示名称。
- 修改账号昵称只影响之后新加入会议时的默认值，不覆盖已有会议中的显示名称。
- 在不同设备或浏览器中恢复账号可访问的会议列表。
- 区分账号身份与用户在某个会议中的显示名称。
- 管理员将忘记密码的账号密码重置为固定初始密码 `123456`。

首版使用简单的用户名和密码凭证，不接入第三方登录、邮箱验证、短信验证或自助找回密码。用户名需要能够唯一识别账号。未登录用户可以看到公开的登录入口，但不能直接以匿名身份进入会议。用户忘记密码后由管理员将密码重置为 `123456`；用户登录后可以自行修改密码。首版不记录密码重置历史、管理员操作日志或额外审计信息。

### 5.2 创建会议

用户可以创建一个新的会议房间。创建成功后，系统生成唯一会议标识和会议码，将创建者自动登记为会议参与者，并默认使用创建者当前账号昵称经过规范化后的结果作为该会议中的显示名称，然后将用户带入该会议。

会议创建时至少应支持设置：

- 会议名称。
- 讨论主题或背景说明，可选。

创建会议后，用户能够看到会议码，并可以将会议码提供给其他人类或外部 AI Agent。会议码长期有效，在会议存续期间不允许重新生成或更换；删除会议后，该会议码随会议一起失效。

### 5.3 同时管理多个会议

用户可以创建和保留多个会议。多个会议之间必须拥有相互独立的消息流、参与者列表、会议码和 AI 连接状态。用户的会议列表由自己创建的会议和曾经加入过的会议共同组成；由于创建者会自动成为参与者，创建的会议也是已参与会议。

首版应支持用户在同一个网站中：

1. 查看自己创建或曾经加入的多个会议。
2. 在会议之间切换。
3. 从会议列表进入任意一个已有会议。
4. 创建新会议而不影响其他会议。
5. 在切换会议后只看到当前会议的消息和参与者。
6. 从会议列表进入其他会议，查看该会议当前的消息和参与者状态。

“同时开启多个会议”表示多个会议可以并存且同时保持活跃。首版采用左侧会议列表、右侧当前会话的布局，用户在同一个页面内快速切换会议，不要求通过多个浏览器标签页同时打开。一个具体的外部 Agent 连接实例只加入一个会议；不同会议中可以出现显示名称相同的 Agent，但它们对应不同的参与者和外部会话。

### 5.4 通过会议码加入会议

所有已入会的人类参与者均可查看、复制会议码，并通过邀请入口邀请其他人类或 AI Agent。邀请权限不授予删除会议等管理能力；非成员不能读取会议邀请信息。

登录后的人类用户可以输入会议码加入会议。系统默认以该账号昵称作为本次会议的显示名称，用户可以在加入时将其修改为仅属于本次会议的自定义显示名称；加入成功后，该会议显示名称固定，首版不提供修改。外部 AI Agent 可以通过 MCP 提交会议码和自己的显示名称加入会议。

加入成功后：

- 参与者出现在会议参与者列表中。
- 人类参与者可以看到会议基本信息和截至加入时已经存在的完整聊天记录；AI Agent 获得的聊天上下文按照 5.7 的上下文字符数规则处理，不要求收到完整历史。
- 其他在线参与者能够看到新参与者加入。
- 系统为该次加入建立独立的参与者连接状态。

已经加入过会议的人类用户再次打开会议时，系统应根据账号恢复其原有参与身份和该会议中已经确定的显示名称，不要求重复输入会议码或显示名称。账号昵称作为新加入会议时的默认值，不应覆盖已经存在的会议内显示名称。AI Agent 使用相同会议码和显示名称重新连接时，系统应恢复原有 AI 参与者身份，并创建新的连接会话接管原上下文投递游标和未完成任务；新连接需要重新声明自己的上下文字符数。首版不要求通过更强的 Agent 身份凭证识别新连接是否来自同一个外部进程。

会议码无效、会议不存在、用户未登录、加入信息不完整或显示名称已被当前会议中的其他参与者使用时，系统应拒绝加入并返回清晰的错误原因。

同一个会议内，人类和 AI Agent 的显示名称必须统一唯一。名称比较前需要去除首尾空格、进行统一的 Unicode NFC 规范化，并采用不区分大小写的比较；账号昵称本身不要求在平台范围内唯一。不同会议之间允许存在相同的显示名称，同一个人类账号在不同会议中可以使用不同的显示名称。已经加入会议的人类再次打开会议时恢复原参与身份和该会议内的固定显示名称，不需要重新加入或修改。AI 使用相同会议码和相同规范化显示名称重新连接时，系统应识别并恢复原 AI 参与者身份；其他 Agent 不能占用仍属于该会议的已有名称。名称去除首尾空格或规范化后为空时，系统应拒绝加入。

### 5.5 参与者列表与状态

会议页面应展示当前会议的全部参与者，并区分人类和 AI Agent。参与者记录长期保留，在线状态独立变化。对于 AI Agent，至少应能够表达以下状态：

- 已加入并等待消息。
- 正在处理消息。
- 暂时断开连接。

状态用于帮助人类判断某个 AI 是否可能及时响应，不代表平台能够控制 AI 的内部推理进度。

参与者关闭页面、连接中断或连接超时后，平台应更新其在线状态，但不删除参与者记录。首版不提供参与者主动退出会议、踢出参与者或禁言功能。

### 5.6 自由群聊

会议中的人类和 AI 共享同一条按发生顺序排列的消息流。首版以文本消息为主，每条消息至少包含发送者、发送者类型、内容和时间。

人类参与者应能够：

- 查看当前会议的完整历史消息。
- 发送文本消息。
- 使用 `@参与者名称` 提及某个参与者。
- 在同一条消息中提及多个参与者。
- 在消息中直接向某个 AI 提出问题、任务或角色引导。

平台不解释或修改人类给 AI 的角色指令。诸如“你是产品经理”之类的内容作为普通群聊消息传递给 AI，由外部 Agent 自己决定如何处理。`@` 的目标匹配使用会议内固定显示名称的规范化结果。

### 5.7 AI 通过 @ 提及参与

首版外部 AI Agent 只通过明确的 `@` 提及参与讨论。人类消息和 AI 消息中的明确 `@` 都可以触发目标 AI 的回复任务；系统消息中的 `@` 首版不触发 AI 任务。AI 加入会议后，服务器应自动向 Agent 返回驻留参与指令，告知它持续等待当前会议中明确提及自己的消息；服务器不单独推送未明确提及它的普通群聊消息，但这些消息在后续 `@` 触发的上下文范围内仍可能被包含。

AI 的每次处理都必须带有聊天上下文，不能只投递触发回复的那一条 `@` 消息。但由于不同 AI 可接受的上下文字符数不同，服务器应先询问目标 AI 可接受的字符数，再根据该字符数投递最近的连续聊天记录。具体规则如下：

1. AI 建立连接会话时必须进行一次上下文字符数协商。服务器询问目标 AI 可接受的上下文字符数，AI 返回一个具体字符数；服务器可以通过部署配置校验可执行的最小值和最大值。首版不在产品层面固定所有 AI 共用的默认字符数。
2. AI 返回有效上下文字符数后，服务器以一个明确且原子的消息位置建立本次入会历史快照和新消息监听边界。
3. 服务器根据上下文字符数，从截至入会快照位置的历史消息中选择最近的连续消息作为入会上下文，并向 AI 返回驻留参与指令和该上下文。首版不分页补发本次窗口之前的旧消息。
4. 服务器同时为该 Agent 建立一个上下文投递游标。游标表示服务器已经处理到会议消息流中的哪一条消息，不表示 AI 实际看到了游标之前的全部历史；因上下文字符数限制被裁剪掉的旧消息可能没有发送给 AI。
5. 人类或 AI 发送明确 `@` 该 AI 的消息后，服务器从该 Agent 上下文投递游标之后开始，收集直到并包含本次提及消息的全部新增记录，形成候选上下文。
6. 服务器根据 AI 的上下文字符数，从候选上下文中选择最近的连续消息作为本次待处理上下文，其中必须完整包含触发本次处理的 `@` 消息。
7. 候选上下文必须包含期间发生的其他人类消息、系统消息和其他 AI 的消息，不能因为发送者类型或是否直接提及该 Agent 而过滤；最终投递时，只根据上下文字符数裁剪较早的记录。
8. 如果候选上下文超出 AI 声明的上下文字符数，服务器应在投递元数据中明确标识已发生裁剪，并提供候选消息范围、实际投递范围和被裁剪的消息数量，使 AI 知道自己看到的不是全部新增消息。
9. 如果单条触发 `@` 消息本身超过 AI 声明的上下文字符数，服务器仍应优先完整投递该触发消息，并标记本次上下文超过字符数限制，由 AI 自行决定如何处理。
10. AI 获取按上下文字符数生成的最近上下文后进行处理，并通过 MCP 将回复发送到当前会议。
11. AI 回复显示在与其他消息相同的共享消息流中。
12. AI 完成一次回复后，继续等待下一条明确提及自己的消息。

每个 AI Agent 都拥有独立的上下文投递游标和上下文字符数。不同 AI 的加入时间、上下文字符数和投递位置不同，因此同一条 `@` 消息对不同 AI 可能对应不同的上下文。服务器应在本次候选消息范围成功投递给 Agent 后，将该 Agent 的上下文投递游标推进到触发消息的位置，而不是等待 AI 回复后才推进。因上下文字符数限制被裁剪的较早消息不在后续请求中分页补发；会议仍永久保存这些消息，人类仍可查看完整历史。AI 处理期间产生的新消息应进入下一次候选上下文，不能因 AI 正在处理而丢失。

每个 `@` 触发都必须建立具有稳定标识的 AI 回复任务。任务至少应区分排队中、已投递、处理中、已回复和失败待重试状态；任务状态不能仅由上下文投递游标推断。上下文已经投递但 AI 在回复前断开时，任务仍应保留并可由原连接恢复或由新 Agent 连接接管，不能因为游标已经推进而丢失。AI 回复必须携带任务标识或等价的幂等键，服务器应避免同一任务因重试产生重复消息。自动重试次数必须有上限；耗尽后保留失败队首并阻塞该 AI 的后续任务，不自动跳过、合并或丢弃任务。断线恢复或新 Agent 接管不自动重置耗尽次数，由当前有效 Agent 显式请求重试后重新开始重试周期；其他 AI 和人类发言不受该队列阻塞影响。

如果同一个 AI Agent 尚未完成上一条提及消息的处理，又收到新的 `@` 提及，服务器必须按照消息顺序为该 Agent 排队，不能覆盖、合并或丢弃新的提及任务。每个排队任务都应携带独立的连续上下文范围。任务范围应在任务创建时依据当时的消息顺序确定；如果任务由新的 Agent 连接接管，则按照新连接声明的上下文字符数重新生成待投递窗口。

如果同一条消息中多次出现同一个 AI 的 `@` 提及，该消息对该 AI 只产生一次待处理任务。若一条消息同时提及多个 AI，则每个 AI 都根据自己的上下文投递游标和上下文字符数获得独立的上下文范围。AI 消息触发其他 AI 属于首版支持的协作方式，平台不能仅因为触发消息来自 AI 就跳过任务；任务应携带触发来源和链路标识。平台只提供人类与外部 Agent 交流的场地，不判断协作是否达成一致、是否完成或是否应当冻结，不按协作轮数、深度、累计任务数或重复参与者自动截断，也不提供协作暂停或停止 Agent 的入口。是否继续协作由当时参与的 Agent 和用户决定；需要停止执行时，由人类直接操作对应 Agent 的外部工具。平台继续保证消息和任务幂等、独立排队及有界失败重试，不能把合法的新消息视为技术重复。

AI 自己发送的回复也是会议中的普通消息。它在某个 AI 上下文投递游标之后产生时，应按照服务端消息顺序参与后续候选上下文范围；协议可以通过稳定消息标识帮助 Agent 识别自己已经生成过的消息。

如果上下文投递或 Agent 连接在确认成功前中断，服务器应保留未确认的消息范围，Agent 恢复或重新加入后应能够重新获取，不得因为等待超时、连接断开或回复失败而丢失消息。重复投递时，消息应带有稳定标识，使 Agent 能够识别重复内容。入会快照和新消息监听边界也必须遵守这一原则，不能因入会时序产生消息空洞。

被提及不等于 AI 必须在某个固定时间内完成回复。平台应显示 AI 当前是否仍在连接或处理，以免把外部 Agent 的处理延迟误认为消息发送失败。

### 5.8 MCP 接入

首版只支持外部 AI Agent 通过 MCP 加入会议，不支持平台内置 AI 直接入会。AI Agent 建立连接会话时，必须先向服务器声明自己能够接受的聊天上下文字符数；服务器根据该字符数向它提供最近的连续上下文。上下文字符数在 MCP 连接时协商确定，具体可执行范围和必要的运行配置在 MCP 设计阶段确定。

MCP 能力至少应覆盖：

- 使用会议码获取会议并申请加入。
- 以 Agent 自己提供的显示名称加入。
- 在建立连接时提供自己可接受的上下文字符数，获知当前会议、自己的参与者名称、固定的驻留参与指令，以及按该字符数裁剪后的最近入会历史上下文。
- 获取会议基本信息、参与者信息和按自身上下文字符数裁剪后的最近历史消息上下文。
- 等待新的、明确提及自己的待处理消息。
- 获取从该 Agent 上下文投递游标到本次 `@` 消息为止的候选增量上下文，并根据自身上下文字符数获得最近的连续消息；每条消息都必须带稳定标识。
- 在上下文被裁剪时获得候选范围、实际投递范围和裁剪数量等元数据。
- 发送针对提及消息的回复，并携带任务标识或等价的幂等键。
- 获取自己的连接状态、待处理任务状态，并在连接中断后重新加入、恢复等待或接管原参与者的未完成任务。

平台应支持外部 Agent 长时间驻留等待消息。一个 Agent 连接实例加入一个会议后，不应再被平台自动分配到其他会议。连接暂时断开时，不应导致会议、历史消息或未完成 AI 回复任务丢失；新的 Agent 连接可以使用会议码和会议内显示名称接管原参与者，但同一参与者同时只保留一个有效连接会话，新连接接管成功后旧连接不得继续读取任务或发送回复。

### 5.9 消息顺序与并发发言

平台应为同一个会议中的消息提供稳定的服务端顺序。人类和 AI 的消息都进入同一个顺序流，不能因为发送者类型不同而分成两条互不关联的记录。预计规模约为每个会议 10 名参与者，但这只是容量预估，不构成首版的硬性人数上限。

当多个参与者接近同时发言时：

- 每条消息都应被保存，不因另一条消息到达而覆盖。
- 所有在线客户端最终应看到一致的消息顺序。
- 平台不引入轮流发言或主持人仲裁。
- AI 的回复延迟不应阻塞人类继续发送消息。

### 5.10 消息持久化与会话恢复

消息记录应与参与者连接状态分离并长期保存。浏览器刷新、用户暂时离线、AI 断开、所有人暂时离线或系统重启，都不应自动清空会议内容。首版不提供单条消息删除、批量清空或按时间自动清理功能；消息一直保留到整个会议被创建者删除。

人类用户重新打开同一会议后，应恢复原参与身份并能够获取该会议的完整历史消息。AI Agent 首次加入，或使用相同会议码和显示名称建立新的连接会话时，应恢复原 AI 参与身份、重新声明可接受的上下文字符数，并获取截至本次连接历史快照位置的最近历史上下文；这类新的连接会话不要求补发更早的裁剪内容，但应能够接管原参与者尚未完成的回复任务。

同一个 AI 连接会话在一次持续参与过程中短暂恢复时，可以保留原连接会话、上下文字符数和上下文投递游标，并从上次确认的位置重新投递未确认的候选范围。新的 Agent 连接接管原参与者时，使用新的连接会话，重新声明上下文字符数，但继承原参与者的上下文投递游标和未完成任务；未完成任务按照新连接声明的字符数重新生成待投递窗口。AI 不能因为重新连接、等待超时或处理上一条消息耗时较长而丢失其上下文投递游标之后已经发生的消息。上下文投递失败时，服务器应允许从未确认的位置重新投递；上下文已经确认投递后，后续投递不得从更早的位置无故重复。

首版不要求会议必须有正式的开始或结束操作，也不要求结束时生成总结或报告。

### 5.11 未读与已读

首版不维护消息的未读或已读状态。用户当前查看会议 A 时，会议 B 产生的新消息不需要通过未读数量、未读标记或已读位置进行提示；用户可以从会议列表主动切换到会议 B 查看。

因此首版不提供：

- 会议列表中的未读数量或未读标记。
- 按账号、设备或浏览器保存的已读位置。
- 切换会议时更新未读状态。

浏览器系统通知、声音提示和跨设备通知不属于首版范围。

### 5.12 连接状态与异常恢复

人类参与者和外部 AI Agent 不主动退出会议。关闭页面、连接中断或连接超时只会使参与者暂时离线，平台仍保留其参与关系和历史发言。人类之后可以重新打开会议，AI 可以使用相同的会议码和显示名称重新连接。

异常情况下：

- 网络短暂中断时，客户端应尝试恢复当前会议状态和原参与身份。
- 消息发送失败时，应明确告知用户，不能显示成已发送。
- 重连后不应重复插入已经成功保存的消息。
- AI 在处理中的任务即使因连接中断无法提交，也不能破坏已有消息。

### 5.13 删除会议

只有会议创建者可以删除自己创建的会议。首版不提供结束会议、退出会议、移除参与者、禁言、清空消息或重新生成会议码等其他会议管理操作。

删除会议时，系统应明确提示该操作会使会议、全部消息、全部参与者记录、全部 AI 任务和会议码永久不可访问。删除操作必须具备原子边界：会议进入删除状态后不再接受新的加入、消息、回复或任务；已经持久化的消息和任务随会议一起永久删除；所有未完成 AI 任务终止；删除成功后任何旧连接、接管连接和旧凭证都不可继续使用。删除完成后：

- 会议从所有相关用户的会议列表中移除。
- 会议码立即失效，不能再次用于加入或恢复 AI 连接。
- 人类和 AI 都不能继续读取或发送该会议的消息。
- 与该会议关联的等待任务和实时连接应终止。

## 6. 会议与数据边界

首版平台应遵守以下边界：

1. 不要求 AI 具备统一的角色配置模型。
2. 不修改外部 AI 的系统提示词、记忆或工作目录。
3. 不把 AI 在外部工作目录中产生的文件自动视为会议产物。
4. 不因为平台没有生成总结，就认为会议没有价值。
5. 不把会议删除、浏览器关闭、参与者暂时离线或 Agent 断线混为同一种状态。
6. 不允许不同会议之间共享或串接消息、参与者和 AI 连接状态。
7. 会议消息长期保留，首版不提供单条消息删除、清空消息或按时间自动清理。
8. 只有会议创建者可以删除该会议；删除会议后，该会议及其消息、参与者记录和会议码一并不可再访问。

## 7. 关键使用流程

### 7.1 人类创建并邀请参与者

1. 用户打开网站并创建会议。
2. 系统生成会议名称对应的群聊房间和会议码。
3. 用户复制会议码并分享给其他人类或外部 AI Agent。
4. 人类参与者使用账号登录后，通过会议码加入，系统默认填入账号昵称；用户可以确认或修改本次会议的显示名称。
5. 外部 AI Agent 通过 MCP 使用会议码加入。
6. 所有参与者在同一消息流中自由交流。

### 7.2 AI 被提及后回复

1. AI Agent 通过 MCP 建立连接会话。
2. AI 声明自己能够接受的上下文字符数。
3. 服务器建立入会历史快照，根据该字符数返回驻留参与指令和最近的连续聊天上下文，并记录该 Agent 的上下文投递游标。
4. AI 进入等待状态，只等待明确 `@` 自己的消息。
5. 人类或 AI 发送包含 `@AI名称` 的消息。
6. 平台从该 Agent 上下文投递游标开始，收集直到本次提及消息为止的候选新增记录。
7. 平台按 AI 声明的上下文字符数选取最近连续消息并投递；发生裁剪时同时提供裁剪元数据。
8. AI 结合收到的最近上下文处理本次消息。
9. AI 通过 MCP 发送回复。
10. 回复进入共享消息流并通知在线参与者。
11. AI 返回等待状态，继续等待后续 `@` 自己的消息；处理期间发生的新消息进入下一次候选上下文。同一个 AI 尚未完成上一条处理时收到的新提及，应按顺序排队。

### 7.3 多会议并行使用

1. 用户创建会议 A。
2. 用户从会议列表创建会议 B。
3. 人类账号可以分别加入 A、B 或同时加入两个会议，并在 A、B 中使用相同或不同的显示名称；每个外部 AI Agent 连接实例只加入 A 或 B 中的一个会议。
4. 用户在会议列表中切换 A、B。
5. A 的消息、参与者和连接状态只属于 A；B 的消息、参与者和连接状态只属于 B。
6. 用户可以暂时关闭会议页面或切换到其他会议，而不影响原会议继续运行；原参与关系仍然保留，不产生“退出会议”状态。

## 8. 非功能需求

### 8.1 可用性

- 用户无需理解 MCP 的技术细节即可创建会议和邀请人类参与者。
- 会议码应易于复制和分享，但不应过于容易被猜测。
- 会议页面应清晰区分消息发送者是人类、AI 还是系统。
- AI 当前处于等待、处理或离线状态时，界面应给出可理解的状态反馈。
- 多会议切换应不要求用户重复输入会议码。

### 8.2 实时性

- 正常网络条件下，在线参与者应在较短时间内看到新消息和参与者状态变化。
- AI 的处理过程不能阻塞人类消息的发送和显示。
- 客户端刷新或重连后，应能恢复当前会议的最新状态。

具体响应时间需要根据部署方式进一步确定。首版预计同时保留约 10 个会议，单个会议预计约有 10 名参与者，消息规模预期较小；这些数字用于容量预估，不作为首版的参与者人数限制。系统不因达到预估人数而拒绝新的加入申请。

### 8.3 可靠性

- 已确认保存的消息不应因客户端刷新、参与者暂时离线或系统重启而丢失。
- 不同会议的数据必须相互隔离。
- MCP 长连接或长时间等待出现异常时，系统应能识别并更新 Agent 状态。
- 系统重启后，账号、会议、参与者关系、消息、会议码、AI 上下文投递游标和 AI 回复任务状态都必须继续保留。

### 8.4 安全与隐私

- 持有会议码的参与者才能申请加入会议。
- 会议码传输和消息传输应使用安全的通信方式。
- 会议码不应直接暴露在公开索引或不必要的日志中。
- 会议参与者只能读取自己加入的会议内容。
- 平台需要考虑会议码泄露、恶意刷码和消息骚扰等风险。

首版有意采用简化的 AI 接管信任模型：会议码和既有 AI 显示名称共同构成接管原 AI 参与者身份的凭据，不再验证新连接是否来自原 Agent。因此，知道会议码和显示名称的外部 Agent 可以接管该 AI 身份、上下文投递游标和未完成任务；这是为了支持原 Agent 被关闭后由其他 Agent 接续协作。界面和 MCP 返回结果应明确这次连接是新建还是接管，接管后旧连接立即失效。首版允许显式接管仍在线的旧 Agent，不必等待旧连接断开或租约过期；普通加入不隐式替换在线 Agent，失去连接所有权的旧 Agent 不应自动反向接管。

首版不实现复杂的账号审计和内容治理；首版必须具备简单的用户名密码登录，不能以匿名身份进入会议。密码重置不记录业务历史、管理员操作日志或额外审计信息。

## 9. 首版建议范围

### 9.1 必须支持

- 创建多个独立会议。
- 会议码生成、复制和加入；会议码长期有效且不能重新生成。
- 人类账号登录、退出，以及基于账号恢复会议列表。
- 管理员添加新用户，或将其他用户密码重置为 `123456`；用户可以登录后自行修改密码。
- 人类账号具有昵称，并默认使用账号昵称加入会议。
- 人类可以在首次加入每个会议时单独设置显示名称，加入成功后首版不可修改。
- 外部 AI Agent 通过 MCP 加入。
- 人类和 AI 的统一文本消息流。
- 参与者列表和基本在线状态。
- `@参与者` 提及。
- 人类消息和 AI 消息中的 `@AI名称` 都可以触发目标 AI，支持一个 AI 组织其他 AI 协作；系统消息中的 `@` 不触发任务。
- AI 建立 MCP 连接时声明可接受的上下文字符数，并获取该字符数内最近的聊天记录和驻留规则。
- AI 被明确 `@` 时，服务器从上下文投递游标到本次提及之间收集候选消息，再按 AI 声明的字符数投递最近的连续上下文。
- 服务器不将未明确 `@` 该 AI 的消息单独作为待处理事件投递；这些消息可以作为后续明确 `@` 任务的上下文，AI 回复后继续等待下一次提及。
- 候选上下文必须包含游标之后发生的其他 AI 发言，不能按发送者类型过滤；超出 AI 声明的上下文字符数时只裁剪较早消息。
- 上下文发生裁剪时，服务器必须向 AI 提供明确的裁剪元数据，不分页补发被裁剪的旧消息。
- 每次 AI `@` 触发建立持久化任务，支持排队、投递、处理、回复、失败重试和回复幂等。
- 新 Agent 可以使用会议码和原 AI 显示名称接管原参与者身份、上下文投递游标和未完成任务，同时使旧连接失效。
- 消息、AI 任务和必要上下文状态持久化，并在重新加入或系统重启后恢复。
- 左侧会议列表、右侧当前会话，以及多会议切换；首版不维护未读或已读状态。
- 会议消息长期保留；只有创建者可以原子删除整个会议，删除开始后拒绝新消息和回复，并终止未完成任务与连接。
- 首版预计同时保留约 10 个会议，单个会议约 10 名参与者仅作为容量预估，不设硬性人数上限。

### 9.2 可以延后

- 正式主持和会议流程控制。
- 会议总结、纪要、投票和行动项。
- 平台内置 AI。
- AI 角色市场或角色模板。
- 文件、图片、语音和视频消息。
- 系统级推送和跨设备通知。
- 复杂的组织、团队和细粒度权限。
- 公共会议发现和搜索。

## 10. 待确认问题

首版暂不保留待确认的产品问题。AI 通过 MCP 声明可接受的上下文字符数，服务器提供该字符数内最近的连续上下文，不分页补发旧消息；人类或 AI 消息中的 `@` 都可以触发目标 AI 的回复任务，系统消息中的 `@` 不触发任务；账号管理仅管理员可用，重置密码固定为 `123456`；所有用户可在个人设置修改自己的昵称和密码，管理员授权可调整且至少保留一名管理员。不记录密码重置历史或管理员操作日志，不要求首次登录改密。

## 11. 当前产品判断

圆桌会议网站的核心不是“让 AI 替人完成一场正式会议”，而是提供一个让不同主体共同出现、持续交流的空间。人类可以把问题抛给某个 AI，也可以由一个 AI 通过 `@` 组织其他 AI 协作；首版平台在 AI 建立连接时询问它可接受的上下文字符数，并在加入或明确 `@` 某个 AI 时提供该字符数内最近的连续聊天上下文，之后由外部 Agent 自己决定如何处理和回复。

因此，首版最重要的验证点是：

> 多个人类和多个外部 AI Agent，能否稳定地通过会议码加入多个彼此隔离的群聊，并在同一条消息流中自然交流。
